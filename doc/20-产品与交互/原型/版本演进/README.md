# D Code 版本界面演进

状态：Confirmed Direction（已确认方向；未来版本尚未进入实施 PRD）

[打开可切换版本的界面演进](dcode-version-evolution.html)

[打开设置“用量与费用”专项探索原型](../dcode-settings-usage-cost.html)（[验证结论与边界](../dcode-settings-usage-cost-验证.md)；当前不绑定具体版本）

本原型用于比较 `0.0.1` 至 `0.1.0` 的用户可见变化。顶部版本按钮切换的是各版本具有代表性的目标工作状态，不表示相应能力已经由当前 Swift App 实现。

已经切入版本的范围、状态与验收记录统一由[版本实施方案](../../../40-版本实施方案/README.md)路由；本页是已确认的版本顺序与差异基线，未来版本只有进入对应 PRD 后才形成冻结的交付范围。

## 最新版本排期

这里的“排期”首先定义交付顺序与版本差异，不承诺尚未进入 PRD 的日历日期。`0.0.9` 不是必须硬塞全部能力的终点；发现新的自用缺口时继续增加 `0.0.10`、`0.0.11`，乃至 `0.0.18+`，直到晋升条件真实成立。

## D 能力吸收规则

- 不设置一个把所有 `d` 开头扩展一次装进 D Code 的总集成版本。前缀只说明能力来源，不定义产品对象、界面位置或版本边界；每项能力都要以一个真实用户结果进入既有模块或独立版本。
- 外部 Pi Extension 的发现、启停、来源与兼容性统一在 `0.0.12` 管理。需要模型主动调用的能力，必须把名称、说明、输入 schema（模式）和执行器注册进同一个 Pi SDK Agent Loop（智能体循环）；Prompt（提示词）只补充发现与选择线索，不能单独构成可调用工具，也不建立第二套 Agent Loop 或工具调度器。
- `pi-dfast` 的成立机制已经由 D Code 自有极速请求策略吸收；`pi-dhashline` 属于结构化文件工具与原生 presenter（呈现器）路径。现有能力继续保留，后续缺口按真实 dogfood 进入 `0.0.18+`，不重新包装成“扩展中心”。
- `pi-dusage`、`pi-dstatus` 一类观察能力优先进入设置、状态或证据界面，不因来源是扩展就强制暴露为模型工具；只有存在明确、可授权的模型动作时才增加小型工具 facade（门面）。
- dgoal / Goal / Work Map 仍属于 `0.2.x` 产品对象，`pi-dteam` / D Team 仍属于 `0.3.x` 执行层；两者可以向模型暴露少量结构化操作，但其状态、生命周期和原生界面继续由 D Code 拥有。

## `0.1.0` 自迭代晋升门禁

`0.1.0` 之后“产品可以自迭代”不是指模型能修改几行代码，而是用户可以留在 D Code 内完成从需求到下一候选版本的主闭环：理解任务、排队补充、观察运行、授予动作、核对差异、验证、构建、重启并恢复任务。

- 至少连续三个 `0.0.x` 候选版本由上一版 D Code 完成主要开发闭环，且每次都保留结构化验证证据；偶然一次自构建不够。
- 至少一次在 Host 退出、构建失败、App 重启或权限拒绝后，从可解释状态恢复并继续；不得靠新开另一套 Agent 工作台掩盖丢失的运行状态。
- 核心闭环不要求用户手动切换 Terminal（终端）、外部编辑器或另一 Agent 产品；macOS、Git、Swift Toolchain（Swift 工具链）与 Pi 仍是被 D Code 调用的真实底层能力，不被复制成第二权威。
- Exact Diff（精确差异）、验证、构建、人工验收、提交、标签与发布分别成立。D Code 可以协助每一关，但未经 507 明确授权不得自动越过提交和发布门禁。
- 最后一个 `0.0.x` 与 `0.1.0` 的主要差异是证据和稳定性晋升；若仍需一个大功能才能称为可用，就继续发布新的 `0.0.x`。

## `0.1.0` 之后的方向

- `0.2.x` 候选方向：Goal / Work Map，建立耐久工作对象、依赖、验收与人工门禁。
- `0.3.x` 候选方向：Agent Profile / D Team，在明确工作对象上增加可观察的多 Agent 执行层。
- `0.4.x` 候选方向：以耐久工作对象为锚点的跨 Session 交接、送达与恢复。

这些方向保留此前研究，但不再挤占 `0.1.0` 前的自迭代基础设施。会话任务看板、Percho、MiniMax Code、Todos 与 `pi-dteam` 都只提供界面或机制参考；D Code 不照搬其云端权威、跨平台外壳、常驻团队、在线市场、远程控制或 TUI 呈现路径。

## 后续版本进入 PRD 前的决策门禁

- `0.0.5–0.0.6` 先固定 Queue Item（队列项）、Run（运行）与 Session / Path 的身份、顺序、取消、恢复和幂等边界。
- `0.0.7` 先由 ADR 固定 Project Trust、Permission Request（权限请求）、授权范围、撤回、审计和无法强制时的诚实降级。
- `0.0.8–0.0.10` 先固定 Git 事实来源、验证证据身份、App 替换 / 回滚与重启恢复协议，避免自更新破坏当前可用基线。
- `0.0.11–0.0.12` 先核实 Pi 实际版本的 Skill / Prompt / Command / Extension 配置、加载与结构化工具注册合同；没有真实写入、重载与读取闭环时只读展示，不建立竞争配置。
- `0.0.13` 先固定 Pi Model Catalog（模型目录）、缓存 / 刷新、`enabledModels` 通配规则、默认模型与当前 Session 模型之间的语义；启停只管理 D Code 选择范围，不得伪装撤销供应商认证或改写历史。
- `0.0.14` 先固定 `models.json` 的校验、原子写入、失败回滚与 Pi 认证交接；任何凭据正文都不得进入 Swift 界面、IPC 或 D Code 自有存储。
- `0.0.15–0.0.16` 先固定编辑缓冲区、磁盘冲突、原子保存、HTML sandbox（沙箱）与本机 / 网络资源策略。
- `0.0.17` 先用 Host、构建、重启、权限和写入中断建立可重复恢复信号，再冻结幂等重试边界。

## 界面语言

产品界面默认使用简体中文。`D Code`、扩展包名、模型名、命令、文件路径和代码标识符保留原文；项目、会话、目标、智能体、上下文、文件、变更和工作清单等产品概念使用中文标签。

## 证据边界

- 每个版本必须在上一版本可运行基线上增加真实能力，不能先显示没有数据和行为的空标签。
- `0.0.1` 就建立最终三栏空间关系；后续版本只向既有区域增加真实能力，不再以重排主界面制造版本变化。
- 工作检查器中的具体值仍是原型样例；“真实”指字段与状态在该版本必须接通真实数据，不表示本 HTML 已读取本机会话。
- 本文件只表达当前版本切割草案；版本范围在对齐完成并进入 `40-版本实施方案/` 前不是交付承诺。
- 当前实现与测试事实仍以项目源码、[架构与运行](../../../10-架构与运行/README.md)和实际验证结果为准。
