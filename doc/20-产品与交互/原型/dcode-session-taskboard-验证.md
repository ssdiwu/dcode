# D Code 会话任务看板原型验证

状态：External Reference（外部参考），调查已收口，未进入版本路线

[打开交互原型](dcode-session-taskboard.html)

## 验证问题

当现有 Pi Session（Pi 会话）被拖入任务看板并建立轻量 Work Item（工作项）引用后，507 是否能直接理解：

- 卡片仍打开原来的同一 Session，不复制历史、不改变 `cwd`；
- 真实运行中的 Session 拖入后自动进入“进行中”，其他默认进入“待处理”；
- 卡片打开原会话后会激活关联工作项上下文，只有该上下文中被 Host 真正接受的 Run（执行轮次）才自动进入“进行中”；
- Run 普通结束不等于可验收；只有确认计划，或 Agent 完成、自验并提交结果后，才进入“待确认”；
- “已完成”只能由用户明确验收；失败、中止、等待回答不会被伪造为完成。

## 假设

如果原会话继续出现在左栏，卡片点击直接回到同一 Session，Composer（输入框）明示当前 Work Item 上下文，并且 Stage（工作阶段）、Runtime（运行状态）与 Gate（人工门禁）分开呈现，用户会把它理解为“原会话 + 稳定工作项引用”，而不是第二套会话存储或一个根据聊天文本猜测的自动化。

## 四列的精确语义

| D Code 列 | 包含的工作阶段 | 进入条件 |
|---|---|---|
| 待处理 | 已收录，没有活动 Run | 拖入时没有可证明的运行事实，或用户手动放置 |
| 进行中 | 排队、规划、执行、暂停与可恢复异常 | 关联 Run 被 Host 接受，或用户手动放置 |
| 待确认 | 确认计划 / 验收结果 | 出现结构化 Plan Gate，或 Agent 完成自验并显式提交结果 |
| 已完成 | 验收成立 | 只有用户明确确认 |

失败不单独成列：卡片保留原阶段并叠加“运行失败”徽标。普通 Question（提问）也不移列，只显示“等待回答”的 User Attention（用户关注）。明确无法继续时，本原型以“需要介入”徽标表达，不为首版提前增加第五列。

## 参考项目与 D Code 取舍

用户截图对应 [`chuspeeism/dashi-taskboard@9b2aeb53`](https://github.com/chuspeeism/dashi-taskboard/tree/9b2aeb53bfe8d40eb5d65feecdfc2cc235928066)。它的卡片是 Issue（议题），底层共有 `backlog / todo / in_progress / in_review / blocked / done / canceled` 七个持久阶段；主区是 `todo / in_progress / blocked / in_review`，空的 blocked 列会隐藏，因此截图通常只见三列。Runtime 只装饰卡片，普通 turn 结束不会自动进 `in_review`；Agent 需完成、验证并显式提交，用户才能确认 Done。

D Code 不照搬独立 Issue 页面，而是让卡片打开原 Session，并用四列压缩表达工作生命周期。生产实现时，Work Item 是稳定对象，BoardPlacement（看板位置）只保存看板成员关系与同列顺序，Session ID 只是关联引用。

## 本次原型包含

- 从左栏拖入或通过菜单加入原会话，重复加入只定位已有卡片；
- 拖入时按已知 Runtime 自动建议“进行中 / 待处理”；
- 卡片主点击打开同一 Session，菜单中另有工作项详情；
- 模拟“提交消息 → Host 接受 → 进行中”、普通结束不移列、自验提交进待确认、用户验收进已完成；
- 鼠标拖动卡片改变阶段或同列顺序，以及 `Shift + ← / →` 的键盘等价操作；
- 失败、需要介入、运行中与人工门禁徽标；
- 每个终态事件必须匹配当前 Run ID；旧 Run 的迟到结果不会结束或推进新 Run；
- 人工移到“待确认”只改变阶段，不会凭空创建计划或结果门禁，也不能直接验收完成；
- “移出任务看板”与 Undo（撤销）。

## 明确不验证

- 真实 Session / Work Item 持久化、搜索、分页或跨重启恢复；
- 真实 `reviewReady`、Plan Gate、失败或阻塞信号已由 Host 结构化发出；
- Goal（目标）、依赖关系、验收证据、多 Run 历史、任务分派或 Agent Team；
- 生产 SwiftUI 拖放、Pi Host、Lease（单写租约）、JSONL、性能或无障碍实现已完成。

## 建议操作路径

1. 将左栏的“正在运行”会话拖进看板，确认建议落在“进行中”；将其他会话拖入，确认默认落在“待处理”。
2. 确认左栏原会话仍然存在，重复拖入不会生成第二张卡。
3. 点击卡片，确认中央切到原 Session，且 Composer 上方显示当前 Work Item。
4. 输入内容并发送，观察“正在启动”过渡；只有模拟 Host 接受后，卡片才自动进入“进行中”。
5. 选“普通结束”，确认卡片不进入待确认；重新启动后选“完成自验并提交”，确认卡片进入“待确认 · 验收结果”。
6. 在待确认中选“要求修改”，确认回到进行中；再次提交并选“验收通过”，确认只有这个人工动作使其进入已完成。
7. 将一个没有 Gate 的卡片人工移到“待确认”，确认只显示“尚无结构化门禁”，不能直接验收；再模拟旧 Run 的迟到结果，确认不会推进新的 Run。
8. 从卡片菜单查看工作项详情，再尝试“移出任务看板”与 Undo。

## 观察信号

- 507 能否在 10 秒内复述“卡片是工作项引用，打开的仍是原会话”；
- “待确认 · 确认计划”、“待确认 · 验收结果”与普通“等待回答”是否可以直观区分；
- 普通 Run 结束、失败、明确无法继续时，看板是否都没有假装任务已完成；
- 用户在 Run 期间手动移列后，迟到的自动结果是否不会覆盖手动选择；
- “移出任务看板”是否足够不像删除或归档。

## 当前结论

原型已将拖入、打开原会话与受控自动流转做成可操作假设，并证明该信息层级可以成立。507 已确认将它保留为外部参考，不纳入 `0.1.0` 前版本规划；`0.2.x` 的 Goal / Work Map 候选方向也必须先固定稳定对象、状态、依赖、验收与证据合同，不预先承诺 Kanban 界面、会话拖放或自动移列。

## 清理状态

原型使用内存模拟数据，无外部网络、文件写入或真实 Session 副作用。当前保留 HTML、本文与原型 README 入口作为 Reference（参考）；后续只有在 507 重新将看板形态纳入某个版本 PRD 时，才恢复生产实现讨论。
