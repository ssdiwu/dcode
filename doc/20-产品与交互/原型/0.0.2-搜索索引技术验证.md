# D Code 0.0.2 搜索索引技术验证

状态：Prototype Evidence（原型证据，临时实现已删除）

## 验证问题

在不修改真实 Pi Session、不给每次按键增加固定等待、也不把多 GiB JSONL 逐次重扫的前提下，D Code 能否用随 App 固定的本机运行时，为中文和英文可见会话正文提供 `P95 ≤ 100 ms` 的本地搜索？

## 假设与信号

- 假设：SQLite FTS5（全文索引）可以作为可删除、可重建的本机缓存；中文需要 D Code 自己生成检索 token（词元），不能直接依赖默认分词器。
- 支持信号：中文两字词、三字词和英文的结果与基准 `LIKE` 一致，放大样本查询明显低于 100 ms，并且不需要新原生依赖或系统命令。
- 否定信号：常见中文短词漏搜、查询退化为全文线性扫描、需要改写 Pi JSONL，或正式依赖与 App 固定运行时不兼容。

## 运行方式与范围

- 使用 App 已固定的 Node `22.22.3` 与其 `node:sqlite`，SQLite 版本为 `3.51.3`，FTS5 可用。
- 真实 `~/.pi/agent/sessions` 仅做只读规模统计与最近会话活动路径抽样；正文不输出到报告。
- 候选数据库与放大样本全部写入 `mktemp` 临时目录，验证后删除。
- 探针没有验证最终 UI、后台调度、缓存损坏恢复或完整生产索引器。

## 观察

- 当前真实目录共有 `1245` 个 Session JSONL，约 `2.480 GiB`；最大单文件约 `486 MB`，正式索引器不能把多个大文件无界并行载入内存。
- 最近 20 个文件共约 `164.755 MiB`；沿当前活动路径排除 thinking、工具输入与工具结果后，得到 `812` 条用户/助手正文，合计约 `0.502 MiB`。可搜索正文与原始日志体积不是同一个数量级。
- 默认 `unicode61` 会漏掉嵌入长句的中文两字词；`trigram MATCH` 不能命中两字词，`trigram LIKE` 虽能命中但属于线性扫描。这两个单独方案均不成立。
- 将 Han（汉字）连续文本预处理为单字与重叠 bigram（双字词），再交给 FTS5 `MATCH`，中文两字词、三字词和英文结果与 `LIKE` 基准一致。
- 在 25,000 条、约 `15.41 MiB` 的放大正文上，两字中文 `trigram LIKE` 中位数约 `26.190 ms`、`P95` 约 `36.031 ms`；bigram `MATCH` 中位数约 `0.093 ms`、`P95` 约 `0.199 ms`。加入原文表关联后，两字计数查询中位数约 `1.273 ms`、`P95` 约 `1.640 ms`。
- 正式候选结构在该放大样本中约 `45.38 MiB`，构建约 `1.617 s`；100 条增量删除约 `0.899 ms`。

## Verdict（结论）

`supported（支持）`：采用 SQLite 原文表与 contentless FTS5（无正文全文索引表），由 D Code 为中文生成单字与重叠双字词、为英文保留标准词元。正式 Host 使用随 App 固定的 Node 运行时，不调用系统 `sqlite3`，也不新增 native addon（原生插件）。

对正式实现的约束：

- 索引只是 D Code 本机缓存，不是会话权威；必须支持删除、版本升级与损坏重建。
- 只索引当前可见 Session 的标题，以及当前活动 Session Path 中的用户和助手正文。
- 首次建立和超大 Session 解析必须有界、可取消且不阻塞聊天协议；Project 取消关联后查询先阻止可见，再清理缓存。
- `node:sqlite` 在固定 Node 22 中仍标为 experimental（实验性）；Host 必须做能力自检，失败时返回明确的索引不可用状态，不能伪装成没有历史。
- 正式实现必须覆盖混合中英文查询编译、Unicode NFKC 规范化、真实片段生成和 Entry ID 定位，不能把探针结果直接外推为产品验收。
