# 活动视图与用户关注状态

状态：Accepted（已接受；约束 `0.0.6` 及后续版本）

## Context（背景）

D Code 的默认 Session Sidebar（会话栏）按置顶、Recent Sessions 与 Project 组织可见 Pi Session，适合定位工作上下文，却不能直接回答哪个 Agent 正在工作、哪个结果刚刚完成、哪个运行正在等待用户。把同一列表简单改成按文件修改时间排序，会丢失用户已有导航模型，也会把“文件最近变化”错误解释为 Run State（运行状态）。

当前 Host 同时只有一个活动 Session，App 在流式运行或 Prompt 事务期间也禁止切换 Session。`0.0.6` 可以建立活动视图与完成关注态，但不能仅凭界面同时画出多个运行圆环，就声称已经拥有后台多会话执行。

Pi Session 仍是会话和消息权威。Activity View（活动视图）需要少量跨重启的“是否已经看过最新完成结果”状态，但这类状态既不是消息，也不能可靠地从 Pi JSONL 的文件时间反推。

## Decision（决定）

1. Session Sidebar 保留两个互斥投影：默认导航继续显示全局置顶、Recent Sessions 与 Project；标题区铃铛切换到 Activity View。切换只替换左侧列表，不创建 Workbench Page、标签、Sheet、信息检查器页面、第二窗口或第二套 Session。
2. 两个投影共享同一可见 Session 集合与稳定 Session ID。Activity View 不扩大 D Code Session Origin、Project / Source Folder 或 Archive 的可见边界；默认导航中的置顶也不改变 Activity View 的活动排序。
3. Activity View 的优先顺序是：等待用户处理、当前实际运行、新完成且尚未查看、其余按最后可证明活动时间倒序。状态相同且时间相同以稳定 Session ID 排序，确保刷新和重启后不会无意义跳动。
4. “正在运行”“等待”“失败”“中止”“正常完成”只能来自 D Code / Host 能证明的 Session Run 生命周期、结构化请求与持久化事实。只有时间而没有 Run 证据的 Session 进入普通时间列表，不推断运行状态。
5. 蓝点是 User Attention（用户关注态），只表示某个稳定 Run / 完成身份的最新结果尚未在对应 Conversation 中成功呈现。它不表示成功、未读消息、正在运行或需要权限；失败和等待使用独立图标、文案与可访问语义。
6. D Code 建立版本化、原子且有界的本机 Attention Store，以稳定 Session ID 与 Run / 完成身份保存完成时间和已呈现状态。它不复制消息正文、Thinking、工具结果或凭据，不写入 Pi JSONL，也不成为会话数据库。
7. 仅打开 Activity View、悬停、聚焦或看到摘要不清除关注态。选择对应 Session 且最新完成结果已经在 Conversation 成功加载并可见后，才确认已呈现；新的完成身份可以再次产生关注态，旧确认不能覆盖更新结果。
8. `0.0.6` 的 Activity View 最多显示一个由当前 D Code 实例实际拥有的运行中 Session。运行期间其他 Session 可保持可见，但若现有所有权边界不允许安全切换，界面必须明确阻止并引导先完成或停止当前 Run，不能宣称它已转入后台。
9. Interaction Dock（交互坞）负责当前 Session 的活动、Follow-up Queue、等待输入、停止、继续和安全重试；Activity View 负责跨可见 Session 的发现与返回。两者消费同一真实 Run / Attention 事实，但不复制状态机或互相取代。
10. 后台多 Session Runtime、跨实例活动、D Team 与跨 Session 调度必须另立并发所有权与恢复合同。以后可以复用 Activity View 的分组和关注语义，但不能倒写成 `0.0.6` 已经支持。

## Consequences（影响）

- 用户既保留稳定的 Project / 置顶导航，也得到一个按当前工作和时间组织的关注入口；Conversation 继续是唯一会话主页面。
- D Code 需要保存一份最小用户关注态，但不会因此复制 Pi Session；删除该派生状态最多让完成结果重新等待确认，不会改变会话历史。
- Run State 与 User Attention 被明确分开：一个 Run 可以已经完成但尚未查看，也可以正在等待用户而不是失败。
- 当前单活动 Session 架构被诚实呈现。实现真正的多个“正在干活的 AI”仍需要后续后台多会话运行合同，而不是视觉扩充。

## Rejected Alternatives（未采用方案）

- **用 Activity View 替换默认会话导航**：会破坏置顶与 Project 的稳定定位价值，让时间排序承担不适合的组织职责。
- **把 Activity View 做成主页面或标签**：会与唯一 Conversation 主页面冲突，并让查看活动打断当前工作上下文。
- **任何完成项永久显示蓝点**：蓝点将失去关注含义，无法区分新结果与已经处理的历史。
- **进入活动列表即清除蓝点**：用户可能尚未看到实际最终结果，会制造已经阅读的假象。
- **以 Session 文件修改时间推断运行状态**：外部写入、普通元数据更新和历史加载都可能改变时间，无法证明 Agent 生命周期。
- **先显示多个运行项、以后再补 Runtime**：界面会对并发所有权、停止与恢复作出虚假承诺。
