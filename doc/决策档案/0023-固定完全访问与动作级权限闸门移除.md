# 固定完全访问与动作级权限闸门移除

状态：Accepted（已接受；约束 `0.0.14` 及后续版本；取代 [0019](0019-Project-Trust-与动作级权限边界.md) 的闸门机制与默认策略）

## Context（背景）

[0019](0019-Project-Trust-与动作级权限边界.md) 在 `0.0.10` 为 D Code Host 内的工具执行建立了动作级闸门：读取放行，bash 与文件写入默认逐次询问，未知工具一律询问，授权按命令前缀 / 授权根持久化，并明确"没有全局'永不询问'开关"。

实际 dogfood 中该机制与唯一使用者的真实工作流不匹配：日常构建、测试、文件编辑被高频打断；而 Pi CLI 本身从来没有任何工具审批（Pi 0.84.1 无内置审批 API，命令与写入直接执行），"D Code 比 Pi CLI 更严格"没有对应的用户价值。`0.0.14` 实施过程中曾先落地"默认完全访问 + 可切换按动作询问"的折中形态，用户最终裁决：**权限是固定语义，不是模式开关**——默认全权限，且不需要任何切换或询问入口。

## Decision（决定）

1. **固定完全访问**：D Code Host 内的 bash、文件写入与自定义工具全部静默执行，不产生权限请求、不询问、不写权限审计。读取类工具行为不变。这与 Pi CLI 的行为一致；D Code 不再比 Pi CLI 多一层门禁。
2. **闸门机制整体移除，而非闲置**：删除 Host 侧 `dcode-permission` 隐藏扩展与 `permission-guard` / `permission-store`（授权表 + 审计的持久化与判定）；删除协议方法 `permission.request / respond / list / revoke / setMode` 与能力位 `permissionGate`；删除 Swift 侧权限请求卡、Composer 权限 chip 与 设置 > 动作权限 页。磁盘上既有的 `~/.pi/agent/pi-dcode/permissions-v1.json` 不迁移、不删除，只是不再读写。
3. **不存在模式或开关**：界面与设置均不提供任何权限档位选择；未来若重新引入门禁（例如多用户 / 团队场景），属于新决策，必须走新的 ADR，不得把本次移除当作"暂时关闭"。
4. **诚实边界**：两种运行环境（D Code 与 Pi CLI）下模型均可静默执行 `rm`、`sudo`、`git push` 等高风险动作；唯一使用者已知晓并接受此敞口。完整形态契约与 `0.0.10` PRD 中与此冲突的条款同步改写或标注取代。

## Consequences（影响）

- 日常 dogfood 不再有任何权限打断；交互坞不再出现权限请求卡。
- `0.0.10` 交付的授权表、审计与权限设置页成为历史；其 PRD 验收条款标注被本决策取代。
- 结构化验证证据账本（ADR 0021）与会话变更账本（ADR 0010）不受影响，仍是事后核对材料。
- 若未来 Pi SDK 引入原生审批 API，D Code 需重新决策是否接入，届时以新 ADR 为准。

## Rejected Alternatives（未采用方案）

- **默认完全访问 + 可切换"按动作询问"**（`0.0.14` 中间形态）：保留了双模式语义、协议同步与两处 UI 入口，对唯一使用者是纯负担；用户明确要求移除。
- **目录内全放开（仅目录外与高危命令询问）**：仍存在打断与第二套"目录内外"语义。
- **维持 0.0.10 默认逐次询问**：即用户正在抱怨的现状。
- **闸门代码保留但默认闲置**：死代码与死协议会误导后续维护，移除更诚实。
