# D Code 编排权威与主会话派生子会话边界

状态：Accepted（已接受；约束 `0.2.x` 的数据准备、`0.3.x` 的 D Team 执行与 `0.4.x` 的跨会话协作）

## Context（背景）

[ADR 0001](0001-Pi-会话作为唯一权威.md)要求 Pi Session 继续拥有持久消息、模型上下文、扩展状态与可恢复运行条目；[ADR 0005](0005-Pi-SDK-与原生呈现边界.md)同时确认 D Code 自己拥有产品对象、生命周期和原生界面，但不建立独立于 Pi SDK 的第二套 Agent Loop 或工具系统。[ADR 0007](0007-会话可见性与-D-Code-创建来源.md)则把普通 D Code 创建会话的 Recent 可见性绑定到稳定来源标记。

未来的 D Team 需要让主智能体派发有界任务、并行观察成员、隔离写入、接收请求与报告，并在 App 重启后恢复可以证明的关系和成果。若所有成员继续复用主 Pi Session，会让对话上下文、单写入租约和变更归因互相污染；若把每个成员只当作一个临时目录或 Pi SDK 内部对象，又无法稳定表达“它属于哪个主会话、哪一轮 Team Run、使用了什么权限与工作空间、结果是否已经处理”。

主会话 ID、子会话 ID、Team Member Run 与执行目录因此必须分层：主会话是协作根，子成员拥有新的 Pi Session，D Code 维护父子关系和执行生命周期，文件系统只承载隔离的工作空间而不成为对象权威。

## Decision（决定）

1. D Code Harness 是位于 Agent Runtime（智能体运行时）之上的产品与编排权威。它拥有 Goal、Work Item、Team Run、Team Member Run、父子引用、当次权限、声明写入范围、可见事件、结构化报告、证据链接与恢复状态；它不自行运行模型或工具，也不复制 Pi 的 Agent Loop。
2. Pi 是首个且在真实第二消费者出现前唯一实现的 Agent Runtime。D Code 的产品对象不得以 Pi SDK 内部类型作为自身身份；Host 只围绕已经需要的创建 / 恢复会话、派发输入、停止、结构化事件、权限请求与报告能力建立最小适配边界，并由适配器明确声明实际能力。不提前设计掩平不同 Runtime 的通用最低公分母 SDK。
3. 用户当前工作的稳定 Pi Session 是 Main Agent Session（主智能体会话），也是 D Team 的协作根。每次 Team Run 必须关联一个确切主会话 ID 和派发时的 Session Path 来源；同一主会话可以先后拥有多次 Team Run，主会话 ID 不等于某一轮团队执行 ID。
4. 每个实际执行 Agent 工作的 Team Member Run 都创建一个具有新稳定 ID 的 Child Agent Session（子智能体会话）。子会话不是主会话中的新 Session Path，也不复用主会话 ID；D Code 持久记录 `主会话 → Team Run → Team Member Run → 子 Pi Session` 的关系。
5. 主、子 Pi Session 的消息、模型上下文、工具结果与 Pi 持久化条目分别继续由各自 Pi Session 权威保存。D Code 只保存不属于会话历史的编排关系、脱敏可见事件、请求、报告和证据引用，不复制完整 Worker Transcript，也不直接修改任一 Pi JSONL。需要成为可恢复会话产物的 Report 或证据必须经 Host 回到相应 Pi Session，或由该会话稳定引用；D Code 本机记录不能成为其唯一副本。
6. 子会话使用可验证的团队子会话来源与父级引用，默认只在所属 Team Run 下导航，不作为普通会话重复进入顶层 Recent 或 Project 会话列表；用户仍可从 Team Run 显式进入并核对其 Pi 历史。Team Run 关闭、成员结束或工作空间清理都不会自动删除子 Pi Session。该规则是 ADR 0007 对 D Team 创建来源的范围扩展，不改变普通 D Code 创建会话的可见性。
7. D Code 可以按主 Pi Session ID 建立受管的执行命名空间，并在其下区分 Team Run 与子会话。逻辑层级为：

   ```text
   <managed-run-root>/<main-pi-session-id>/<team-run-id>/<child-pi-session-id>/
   ```

   目录只表达物理归属，不能替代 D Code 的父子关系记录。具体根路径、目录创建顺序和内部文件布局由 `0.3.0` PRD 与实现验证确定，不成为公开产品身份。
8. 每个具有写入能力的子会话必须使用独立执行目录，不得与主会话或其他写入成员共享同一个可写工作树。Git 项目优先验证隔离 worktree（工作树），非 Git 项目使用受控副本或明确只读降级；这属于 Team Member Run 的执行映射，不把 Session Path 与 Git 分支、快照或工作树绑定。
9. 系统 `/tmp` 只允许用于没有待保留改动、可以随时重建的丢弃式验证。只要工作空间可能包含尚未审查、集成或放弃的用户成果，就必须位于 D Code 管理、不会被系统按临时文件任意清理的恢复范围；只有成果状态已经明确处理后才能清理。
10. 子会话从主会话的协作根派生，但不会自动复制主会话完整历史。D Code 必须提供有界 Context Package（上下文包），至少明确当次任务、必要来源、允许范围、基线、完成信号与回报格式；需要更多上下文时由主智能体或用户显式补充。
11. 单写入边界同时作用于会话与文件：同一 Pi Session 同时最多一个写入者，同一个执行目录同时最多一个写入成员。并行成员只能并行观察共享事实，或在彼此隔离的执行目录中写入；不得把并发覆盖交给事后 Git 冲突作为正常控制机制。
12. 子会话通过结构化 Finding、Request、控制事件、变更 / 验证证据和 Report 回到 Team Run。主智能体负责判断、补充指令、请求用户决定与最终综合；完整成员日志不回灌主对话，隐藏推理不成为产品数据。
13. App 或 Host 重启后，D Code 可以恢复父子映射、可见状态、报告、证据引用与尚未处理的工作空间，并重新观察可用的主、子 Pi Session；不得宣称恢复已经销毁的模型生成、工具调用或 Worker Runtime。状态无法证明时停在未知或待处理状态，不自动重跑、合并或删除。
14. 版本边界固定为：`0.2.x` 只建立 Work Item 与 Session / Team Run 引用所需的耐久数据基础，不因创建工作对象自动启动 Agent；`0.3.0` 交付“一主一子”的首个真实闭环；`0.3.1+` 才增加多个子成员并行、比较与集成；`0.4.x` 继续负责不局限于父子团队关系的耐久跨会话送达、交接与恢复。

## `0.3.0` First Slice（首个切片）

`0.3.0` 只需要证明以下垂直闭环，不以首版团队能力为由一次引入任意数量成员：

1. 用户或主智能体在当前主 Pi Session 中显式启动一轮 Team Run。
2. D Code 创建一个 Team Member Run，在主会话受管命名空间下准备隔离执行目录，并通过 Host 创建拥有新 ID 的子 Pi Session。
3. 子会话接收有界上下文包并独立运行；主界面只显示可以证明的状态、请求、关键发现、证据与结构化报告。
4. 子会话文件活动能关联回 Team Member Run、子会话和执行目录；存在 Git 时仍以实际工作树和 Git 为代码事实。
5. 重启后能够恢复父子关系与未处理工作空间，但不伪装恢复在途 Runtime。
6. 主智能体或用户明确选择继续、接受、集成或放弃；未处理成果不会因成员退出、Team Run 关闭或 App 重启被自动删除。

## Consequences（影响）

- D Code 的产品模型不再等同于 Pi SDK 对象，但当前真实执行仍充分复用 Pi；以后接入第二 Runtime 时可以增加能力适配，而不改写 Goal、Team Run、权限和报告语义。
- 主 Pi Session 保持用户主线程和团队协作根，子成员各自拥有可恢复、可核对的 Pi Session；用户可以从团队摘要进入子会话细节，而不让主对话被完整成员过程淹没。
- 子会话不会铺满顶层 Recent 或 Project 导航，但仍保留可进入、可恢复的 Pi 历史；团队导航状态损坏不能被解释为子会话已经删除。
- 每轮 Team Run 需要额外的会话、磁盘空间、工作树管理、停止与恢复成本；`0.3.0` 必须在权限、精确差异、验证证据和失败恢复基础成立后进入实现。
- 父子关系属于 D Code 自有耐久元数据，目录层级只是实现投影。目录丢失不应伪造会话消失，会话存在也不应伪造工作空间仍可安全继续。
- 父子 D Team 派发与任意既有 Session 间的跨会话消息保持为两种不同合同，避免 `0.3.x` 提前承担 `0.4.x` 的送达与幂等范围。

## Rejected Alternatives（未采用方案）

- **所有成员复用主 Pi Session 的不同 Session Path**：会让独立运行争用同一会话写入权，并把主线程、成员上下文和恢复边界混在一起。
- **以子会话 ID 作为顶层执行根**：能够定位单个 Worker，却丢失它属于哪个主会话和哪一轮 Team Run 的稳定组织关系。
- **所有子会话直接共享同一个可写项目目录**：并发覆盖、Git 状态和变更归因无法可靠隔离。
- **把系统 `/tmp` 当作正式工作空间**：系统清理或重启可能丢失尚未审查和集成的成果。
- **把完整子会话日志复制进主会话或 D Code 数据库**：造成上下文污染和竞争性会话历史，并扩大隐藏推理与凭据暴露面。
- **把所有子会话作为普通 Recent / Project 会话平铺**：丢失主从层级并让后台成员挤占用户的主工作导航。
- **现在先造支持任意 Agent Runtime 的通用 SDK**：没有第二个真实消费者，容易引入假抽象或丢失 Pi 已有能力；当前只保留最小、可声明能力的适配接缝。
