# 自构建与受控重启协议

状态：Accepted（已接受；约束 `0.0.13` 及后续版本）

## Context（背景）

`0.1.0` 晋升门禁要求"至少连续三个 `0.0.x` 候选由上一版 D Code 完成主要开发闭环"，其前提是第一次自构建闭环：在 D Code 自己的会话内完成改动、验证、构建候选 App、受控替换 / 重启并回到原任务。风险核心是替换正在运行的 App——构建过程绝不能触碰在用 bundle，替换必须是可回退的原子动作，且"一次成功"不得被表述为稳定自迭代或后台静默更新（路线显式反目标）。

## Decision（决定）

1. **构建隔离**：`app/build.sh` 支持 `PI_DCODE_DIST_DIR` 覆盖产物目录；D Code 的"构建候选"动作输出到 `dist-candidate/`，构建前清除旧候选防陈旧冒充。在用 `dist/D Code.app` 在整个构建过程中不被触碰；构建失败只保留输出尾部（200 行）并如实报告。
2. **候选校验**：重启动作前校验 `codesign --verify --deep --strict`、Info.plist App 版本、内嵌 Host `package.json` 版本一致性，以及 `0.0.27+` 候选内 `DCodeRelaunchHelper` 存在且可执行；任一不过拒绝替换。`0.0.26` 起还须满足 [ADR 0031](0031-自迭代候选来源快照与本机分发边界.md) 的显式源码 checkout、固定自动门禁、签名前 Candidate Manifest 与构建前后来源稳定性约束。
3. **受控替换与独立交接**：只由用户在设置“自进化”页显式触发（带确认）——安全保存 Composer draft / Follow-up Queue → 完整校验 Candidate → 在交换前把当前 bundle 的 `DCodeRelaunchHelper.app` 暂存到稳定位置；首次从不含 Helper 的旧 active 升级时，允许改从已经完整校验的 Candidate 暂存 → 持久化 typed restart intent，Full Receipt 还须已经持久化 `restart_requested` → 暂存旧 backup → `mv 当前 → D Code.app.backup` → `mv 候选 → D Code.app` → 完成当次不可逆回执事务（如 Self-evolution rollback）→ 在旧 App 仍存活时通过 LaunchServices 启动独立 bundle ID、无界面的 Helper App。Helper 以独立参数接收旧 App PID、规范化的 `dist/D Code.app` 路径与有界超时；它等待旧 PID 真正消失，再等待固定 3 秒完成 macOS 单实例生命周期清理，仅移除继承自旧 App 的 `__CFBundleIdentifier`，随后用 `open -W <绝对 App 路径>` 完成系统交接；`LSMultipleInstancesProhibited` App 不使用 `-n`。从 `NSWorkspace.runningApplications` 核对路径相同、PID 不同的新实例，并在 1 秒后再次确认同一 PID 稳定存在，再保留 5 秒有界请求方交接窗口；zombie PID、短暂进程和命令退出码都不构成启动成功。当前 App 在 Helper App 成功启动后才提交旧 backup 暂存并请求退出；不得在旧实例存活时预先启动目标 D Code。receipt finalize 或 Helper App 创建失败时不退出当前 App：不可逆回执尚未完成时精确恢复 active / backup / candidate 三条交换前身份并清除未启动 marker；不可逆 rollback 回执已经完成但 Helper App 无法启动时不反向伪造 bundle 状态，保留目标 App 与 marker，要求用户退出当前实例后手动打开。失败事务绝不能留下随后意外拉起 D Code 的孤立 Helper。超时或新 App 启动失败时保留 marker、目标与 backup，不自动重试。
4. **回滚**：backup ↔ 当前交换后继续使用同一 relaunch helper；Bootstrap recovery、普通 Self-build、Full Self-evolution 与 Self-evolution rollback 不建立各自的启动实现。无 watchdog、无崩溃自动回滚；若 helper 超时或新构建无法启动，保留可核对的 marker 与 backup，允许人工恢复。
5. **会话恢复**：重启前记录 `pendingSessionId`；新 App 启动时只读 restart intent。Host 就绪并按打开即接管（ADR 0018）成功恢复同一 Session，且对应 receipt 已安全推进后，才 acknowledge / 清除 marker；恢复失败时 marker 与 receipt 跨重启保留。自动恢复、通知回跳等直接 `openSession` 路径在提交真实 Session 前必须先停靠可能并发激活的主页草稿，不能让 transcript 已恢复而 Composer 仍显示“新会话 Project”托盘。
6. **闭环分工**：会话内的改动 / 测试沿用既有工具与权限闸门（0.0.10），验证命令由证据账本（0.0.12）自动入账；"至少一条真实任务完成构建-重启-恢复"是人工验收的完成信号，不由机制交付自动宣称。

## Consequences（影响）

- D Code 具备最小的可信自构建机制；后续版本可重复该闭环积累 `0.1.0` 门禁所需的连续证据。
- Helper 先等待旧 PID 完全退出，再启动一次新 App，因此不存在两个 D Code 实例并存的正常路径；超时或启动失败只保留可恢复证据，不猜测重试。
- 备份只保留一份；跨多版的回滚历史不进入本协议。

## Rejected Alternatives（未采用方案）

- **构建直接覆盖在用 bundle**：运行中替换资源会导致新旧行为混合，不诚实且不可回退。
- **watchdog / 崩溃自动回滚**：首版闭环复杂度过高，且掩盖用户应知的失败。
- **Sparkle 式后台自动更新**：与"后台静默更新"反目标直接冲突。
