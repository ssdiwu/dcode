# 后续消息队列所有权与派发边界

状态：Accepted（已接受；约束 `0.0.5` 及后续版本）

## Context（背景）

D Code 当前只允许一个 `session.prompt` 写入正在活动的 Pi Session。运行期间 Composer 会禁用发送，Protocol v1 也明确拒绝 `streamingBehavior`；用户只能等待当前 Session Run 结束、打断它，或在别处暂存下一步意图。

当前固定的 Pi `0.84.1` Runtime 提供内存中的 `followUp` 队列，但公开合同只支持读取队列或整体清空，不支持 D Code 产品要求的稳定单项身份、逐项编辑、调整顺序、撤回、跨重启恢复与派发幂等。把这份运行时队列直接当成产品权威，会让界面无法诚实回答一条意图是否仍可修改、是否已经进入 Pi、崩溃后是否会重复发送。

同时，[ADR 0001](0001-Pi-会话作为唯一权威.md)要求 Pi Session 继续拥有会话历史，[ADR 0006](0006-共享观察与按需写入.md)要求所有会话写入经 Host、Pi SDK 与 Session Lease 完成。`0.0.5` 因而需要一条明确的所有权转移线，而不是建立第二套消息数据库。

## Decision（决定）

1. D Code 只拥有尚未派发的 `Queue Item（队列项）`。每项具有稳定、不可复用的 Queue Item ID，并绑定入队时的稳定 Session ID 与 Path Lineage Anchor（路径谱系锚点）；正文以版本化、原子、有界的本机状态耐久保存，但不写入 `~/.pi/agent`。锚点是当时路径上的稳定 Entry ID，不等同于会随消息追加变化的当前叶节点。
2. Queue Item 在派发前不是 Pi 消息、Session Path 节点或模型上下文。界面必须称其为“待派发”，不得把本机保存、进入派发门禁或 Host 接受请求显示成“已发送”或“已执行”。
3. 同一 Session / Path 内默认按先进先出顺序排列。用户可以在仍为待派发状态时查看、编辑、调整顺序或撤回；进入派发转换后该项即锁定，管理动作不能与派发并发修改同一正文或身份。
4. Follow-up Queue 不 steer、不取消也不改变当前 Session Run。当前 Run 或同一队列已确认派发产生的条目可以把 Path Lineage Anchor 沿唯一的已确认后继推进，这属于路径正常生长而不是漂移；用户选择兄弟路径、从旧消息另起路径、外部写入或无法证明来源的叶节点变化不得自动重绑。D Code 只有在前一 Run 已取得正常收口证据、没有等待用户输入或权限决定、绑定谱系仍成立且普通写入门禁成立时，才取出一项交给 Host。每次只允许一项处于派发或运行状态；该项完成后再重新评估下一项。
5. 派发继续复用 `session.prompt`、Write Intent、Session Lease、写入前后指纹核验与冲突处理。Queue Item ID 必须稳定关联本次 Prompt ID 与 Host 返回的持久化用户 Entry ID；只有收到 Session ID、Prompt ID 与 Entry ID 均匹配的 Pi 持久化证据后，该项才退出待派发所有权并成为 Pi Session 的普通用户消息。
6. D Code 的本机记录在所有权转移确认前必须保留。重启后可以根据耐久派发收据恢复已确认状态；如果崩溃或断连使派发结果无法证明，D Code 保持该项为“派发结果未知”并停止自动重试。恢复路径可以核对后继续或由用户决定，但绝不能用再次发送来猜测上一次没有生效。
7. 当前 Run 失败、中止、等待用户输入、等待权限、Host / Lease 中断、Session 或 Path 身份变化、外部写入冲突，以及派发结果未知，都会保留尚未确认转移的队列并停止自动派发。切回原 Session / Path 不足以越过“结果未知”；身份漂移后的恢复必须由用户显式继续。
8. 队列 Store 损坏或不支持时保留原始字节、禁用新增和自动派发并显示可操作错误；写入失败不清空 Composer Draft 或既有 Queue Item。普通 Pi Session 的观察、历史阅读与安全的非队列操作保持可用。
9. `0.0.5` 只接受普通文本。斜杠命令、Skill / Prompt / Command 资源、图片、附件、Path Action、Extension Request、Steer 与跨 Session 消息不进入队列；以后扩展任何类型都必须重新确认其序列化、权限、恢复与所有权合同。
10. `0.0.5` 只在 Composer 附近提供最小队列表面。会话栏 Activity View、完成关注态，以及当前活动、等待输入、停止、重试与队列的统一状态机属于 `0.0.6`；Goal / Work Map、多 Agent 与跨 Session 调度不由本 ADR 提前定义。
11. 只要一个 Session 仍有待派发、正在派发或结果未知的 Queue Item，就不能把该 Session 移入废纸篓；用户必须先安全确认或撤回这些项目。Archive 只隐藏普通导航并保留队列，Session Copy 创建新身份且不继承源队列。
12. 从 `0.0.7` 起，运行中的 Composer 同时提供“立即介入”和“排队等待”两个显式发送方式。“排队等待”继续完全遵守本 ADR 的耐久 Queue Item 合同；“立即介入”不是 Queue Item，而是携带预期 Run ID 调用 Pi 专用 `AgentSession.steer()`，在当前工具安全结束后、下一次模型调用前进入同一 Run。Run 身份已变化即拒绝；D Code 在 Pi 接受前先保留当前路径草稿，Run 正常完成后才清除，拒绝、失败、中止、Host 中断或结果未知都会把正文恢复到 Composer。结构化等待、停止请求、斜杠命令和路径草稿不得使用 steer。

## Consequences（影响）

- 用户可以在当前运行不被打断的情况下继续表达下一步，并在真正派发前修正或撤回；重启不会把纯内存队列静默丢失。
- D Code 会保存一份尚未派发的意图正文，但它不是竞争性会话库：记录只覆盖所有权转移前的 Queue Item，Pi 持久化确认后由 Pi Session 独占消息事实。
- Pi 自带的内存 `followUp` 可以作为一次派发过程中的内部机制，但不能成为产品队列、恢复事实或用户界面的数据源。
- 分布式写入存在无法证明结果的崩溃窗口时，产品优先停住并暴露未知状态，而不是以“可能重复”换取自动继续。
- `0.0.6` 可以在不重定义队列所有权的前提下，把队列、运行和等待状态收敛到统一控制面。
- `0.0.7` 的 steer 为当前 Run 的主动介入，不承诺中断正在执行的工具，也不取代可编辑、可恢复的 Follow-up Queue；界面必须把两种后果写清楚并允许用户切换。

## Rejected Alternatives（未采用方案）

- **直接以 Pi 内存 `followUp` 队列为权威**：缺少稳定逐项身份、编辑、重排、单项撤回和跨重启恢复合同。
- **入队时立即写入 Pi JSONL**：会把尚可编辑或撤回的意图提前变成会话事实，并要求 Swift 或 UI 状态改写共享会话。
- **只保存在内存**：App 或 Host 重启后丢失，无法满足恢复与不重复派发。
- **把 Follow-up 当作 Steer**：会改变当前运行的输入边界，与“不打断当前工作”的用户承诺冲突。
- **任何终止事件后都自动派发**：失败、中止和等待态不等于正常收口，可能越过用户决定或权限门禁。
- **结果不明时自动重试**：可能把同一意图重复写入 Pi Session，破坏稳定 Queue Item 身份与用户信任。
