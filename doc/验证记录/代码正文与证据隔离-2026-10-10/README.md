# 代码正文、语法高亮与测试证据隔离（2026-10-10）

本记录是 2026-10-10「完整工作台实施」第一片的实际证据：修复上一轮 Markdown／Code Block 迁移遗留的缺陷，并把界面测试的证据输出改为隔离根，避免复跑覆盖历史归档。范围仅限正文代码块与测试证据路径，不含本轮后续切片（输入几何、主按钮、＋入口、来源模型、导航、侧问、动效）。

## 一、修复前先证明缺陷真实存在

四项缺陷都不是从代码外观推断的，每项都有一次「先红后绿」的实际运行记录。

| 缺陷 | 实际表现 | 取证方式 |
|---|---|---|
| 正文代码围栏渲染为空白 | Markdown 里的代码围栏在正文渲染成空容器 | 用 `react-dom/server` 渲染界面真实的 `MessageResponse`，断言代码块内的行文本；修复前 4 条断言全部拿到空串 |
| 高亮缓存键碰撞 | 同语言、同长度、首尾各 100 字相同而只有中间不同的两段代码，第二段直接复用第一段的高亮结果 | 用真实 shiki 先让第一段入缓存，再观察第二段的同步取用结果；修复前返回的是第一段的 token（含 `AAAA…`） |
| 代码语法高亮从未生效 | 所有代码块一直停在未高亮的原始文本 | 渲染进程控制台实际报 `WebAssembly.instantiate(): … violates … 'unsafe-eval' is not an allowed source of script`。原始 token 恰好可读，所以此前没有暴露 |
| 复制按钮把源码渲染成 DOM 属性 | 按钮上出现 `code="export function …"` | 端到端失败时打印真实 HTML 得到 |

## 二、根因与修法

1. **围栏原文取错节点**。hast 结构是 `pre > code > text`，`children[0]` 是 `code` 元素（`value` 为 `undefined`，文本在它的 `children` 里）。改为递归收集子树内的 text 节点，并去掉围栏收尾换行造成的多余空行。
2. **缓存键信息不足**。原键为「语言 + 长度 + 头尾各 100 字」。改为使用完整原文；键里放的是与 React 持有的同一份字符串，不额外占内存。
3. **缓存命中不通知订阅者**。`highlightCode` 在命中缓存时直接 `return`，已注册的回调收不到结果，导致「高亮先完成、代码块后挂载」时永远停在原始文本。改为命中时同样通知。
4. **高亮引擎在真实运行环境不可用**。渲染进程经 `file://` 加载，默认的 WASM(oniguruma) 引擎初始化失败。改用 shiki 的 JavaScript 正则引擎；**没有为此放宽 `script-src`**（试过 `'wasm-unsafe-eval'`，失败形态从抛错变成初始化不返回，仍不可用）。
5. **语言别名被误判为未知**。守卫最初只查 `bundledLanguagesInfo` 的正式 id，而 `ts` 的正式 id 是 `typescript`、`ts`/`cts`/`mts` 是别名，导致整块代码按纯文本渲染、看起来「仍然没有高亮」。守卫改为同时并入官方别名表；真正未知的语言仍退化为纯文本且不丢原文。
6. **复制按钮泄漏源码到 DOM**。`code` 未从透传属性中取出，整段源码被渲染成按钮上的 HTML 属性。已取出，并改用 ref 读取，避免内容变化时重建回调。
7. **正文代码块缺少复制入口**。spec T01 要求复制保持原文，原实现没有入口。补语言标注与复制按钮；复制写入未改写的原文，失败时按钮可访问名变为「复制失败」，状态同时进入 `aria-live`。

## 三、独立审查要求闭合的三项限定修复

首片独立只读审查提出三项限定修复，均在本轮闭合并各有对应证据。

| 修复 | 做法 | 证据 |
|---|---|---|
| 旧环境变量绕过历史目录保护 | `DCODE_VISUAL_SHOTS_DIR` / `DCODE_VISUAL_META_DIR` 原先直接 `mkdir`，等于留了一条直写 `doc/验证记录` 的后门。保留变量名，但两条覆盖路径改走 `assertWritableEvidencePath`，缺省仍回落到隔离根 | 以历史目录设 `DCODE_VISUAL_SHOTS_DIR` 实际导入该模块，被拒绝并抛出原因（正反两侧都验过） |
| 缓存命中时的回调通知无约束 | 补窄公共接口测试：先预热同一 key，再 `highlightCode(key, callback)`，断言回调**确实发生**、结果与同步返回同一份、原文与着色都保持 | `test/runtime/code-block-highlight-cache.test.ts` 新增用例 |
| 双主题没有真正输出 CSS 变量 | `codeToTokens` 加 `defaultColor: false`，两个主题都只输出 `--shiki-light` / `--shiki-dark`；原先浅色被写进内联 `color`，而 span 强制使用 `var(--shiki-light)`，该变量未定义，浅色下关键字与注释同色 | 端到端分别在浅色与深色主题读取关键字与注释的 **computed color**，断言两者不同且与实际背景的亮度差足够；两张截图见下 |

第 3 项顺带暴露并修掉一个会一起上线的问题：原先把 shiki 的 `bg` 内联到 `pre`，等于把浅色主题的 `#fff` 固定住；token 改随主题后，暗色下会变成浅字白底。现改为背景由 D Code 的下沉表面 `--sunken` 承担，`pre` 不再写内联背景与前景色。

### 第二轮复核：手动深色根本没换配色

复核指出第 3 项仍不成立：`TokenSpan` 上的 `dark:!text-[var(--shiki-dark)]` 是 Tailwind 的强制工具类，编译后被包在 `@media (prefers-color-scheme: dark)` 里，而 D Code 的手动深色只切 `html.dark`，**且本项目没有定义 `dark` 这个 class 变体**。结果是手动深色下只有 `!text-[var(--shiki-light)]` 生效：深色背景上仍是浅色主题的标识符蓝（`#005CC5`），对比明显不足。此前那组断言只验「每套内部 keyword≠comment」，两套其实用的是同一套也照样通过——所以它拒绝不了这个缺陷。

修法保持在代码块范围内，不动全局主题机制：去掉 span 与 `pre` 上的两个强制工具类，改由 `styles.css` 里按 `[data-slot="code-block"]` 定位的规则消费 `--shiki-light` / `--shiki-dark`，深色走 `.dark` 前缀。断言同步加强为：

- 同一代表性 token（关键字 `const`、标识符 `keyword`）在浅/深之间 computed 色**必须不同**——这条才真正拒绝「两套是同一套」；
- 低亮度的标识符也纳入可读性对比度检查（此前只查关键字与注释，正好漏掉深色下最暗的那一档）；
- 截图前重新对准滚动位置并断言代码块在视口内，否则证据里根本看不到配色。

加这条断言时它先失败了一次：注释色在两套主题里都是 `#6A737D`（上游 GitHub 配色本就如此），要求它变色等于要求上游换色。已把注释移出跨主题切换的断言，只保留它各自的每主题可读性检查。

### 关于验证命令的出口

本轮早先的若干次运行把结果管道给了 `grep` / `tail`，外层 shell 的退出码被管道掩盖，**不能作为通过依据**。本片后续全部改用保留原始 `output.log` 与 `status.json`、并立即记录真实退出码的方式（`run-check.py`，有界进程组、隔离环境）。已发生的一次中断记为 `exitCode: -15`，**不计为通过**。另注意该脚本会剥离全部 `DCODE_*` 环境变量，因此运行标识改由命令内 `env DCODE_EVIDENCE_RUN=…` 传入。

## 四、测试证据改为隔离输出

`npm run verify` 原先会把产物写进 `doc/验证记录/<带日期的历史归档>/evidence`，复跑直接覆盖旧截图与 JSON。本次改为：

- 统一入口 `test/e2e/evidence-root.mjs`：默认写入被忽略的 `test/e2e/evidence/runs/<运行标识>/`；`DCODE_EVIDENCE_RUN` 可固定目录名，`DCODE_EVIDENCE_ROOT` 可整体重定向。
- `doc/验证记录` 作为只读历史：默认**拒绝**写入（抛错而不是静默改写），确需就地重生成时须显式 `DCODE_EVIDENCE_ALLOW_HISTORY=1`。
- 共 18 个界面工装文件改用该入口：原先硬编码带日期归档目录的 11 个，加上原先写入已被版本控制的 `test/e2e/evidence/`（复跑同样会覆盖旧产物）的 6 个，以及本片新增的 `code-content.test.mjs`。
- 归档流程变为「先跑进隔离根，确认后复制进带日期记录并说明来源」，测试本身不再直接写归档目录。
