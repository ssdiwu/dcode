### P1-3 的续修：目录预审没审完 ≠ 安全

复核发现 `auditSkillEntries` 的失败分支仍不成立，已修：

- **`readdir` 抛错时 `return null`** —— 那等于宣布"审过且没有越界入口"，SDK 照着走进那个目录，预审形同虚设。改为按 errno 分别报 `permission-denied`（`EACCES`／`EPERM`）与 `unreadable`，两者都**不进 SDK**。
- **文件链接与目录链接不再混判**：指向根内的**文件**链接，边界已由 realpath 核过，到此为止——对它再做目录递归只会得到 `ENOTDIR`，把合法文件链接误判成"读不到"。只有**目录**链接才继续审里面的条目。
- **超限不再一律说成 `outside-root`**：层级／条目超预算报 `too-large`。可修的真实原因（权限、超大）被伪装成"有东西跑出去了"，用户就只能去查一个不存在的问题。

红反例（`/tmp/c-p13-red.log`）：把 `readdir` 的 catch 退回 `return null` 后，`test/runtime/references.test.ts` pass 17 / fail 1，新用例报 `目录读不到时预审没审完，SDK 不得进入`（`true !== false`）——即 SDK **确实**在无权限目录上跑过并给出了诊断。把映射一并退回旧写法（一律 `outside-root`）后，层级超限的 issue code 实测为 `outside-root`、`too-large` 为 `false`，证明另一半断言同样能区分。

复核代理在本轮指出一条**覆盖缺口**：条目预算必须**跨递归累计**，若每层各自重新给满额度，深层目录就能把总量顶穿而预审仍显示"审完"。已补第三条反例（5 层 × 1000 条目 = 5000，单层都不超预算），并回检（`/tmp/c-p13b-red.log`）：把预算改成不共享后，新用例报 `条目预算累计超限时预审没审完，SDK 不得进入`（`true !== false`）；恢复后 18/18（`/tmp/c-p13b-green2.log`）。

新用例的可观察判据沿用上一条：每个夹具根里都有**畸形技能**，SDK 读到必然产生 `skills-unavailable`；同一批的合法根同样有畸形技能且**确实**有该诊断，所以"没有诊断"不是恒真。保留的对照：根内**普通文件符号链接**、根内**嵌套合法目录**、已知外链 `SKILL.md`（报 `outside-root`）都照常可用，未被这次收紧误伤。目录权限一条在动手前先探测 `readdir` 是否真抛 `EACCES`（本机生效），不生效就只报诊断、不做断言。

### 再修：根内链接环与三条无证据的 fail-closed 分支

第二次增量复核指出的问题——**安全属性未被推翻**（各路径在真实实现里逐条查过都是 fail-closed），但有一处**误伤**和三条**没有证据**的分支：

- **根内链接环被误报**（实现缺陷）：`.pi/skills/loop -> .pi/skills` 让预审反复重入同一目录直到撞上深度上限，于是报出**不真实的成因** `too-large: 层级超过 6`，并把本来合法的技能全丢掉——根内链接环不是"审不完"。修法：递归携带 `seen` 集合，已审过的真实路径不再重入。
- **`rel === ''`**：链接指向工作空间根**本身**时，它在根内（不是越界），但已跳出技能子树、预算内审不完。说成 `outside-root` 是撒谎，说成审完同样是撒谎——按 `too-large` 报并写明"已跳出可审范围"。
- **判不出类型时不再默认安全**：`stat(real)` 失败原先回落成"是文件、不递归"。> **本条已被下面的「验收补证」一节取代**：中间的"改为继续审"写法同样不合格（把错误吞成 `true`），最终改为按 errno 给出可辨原因。以验收补证一节为准。
- **三条分支补夹具**（此前只有变异检查、仓库里没有对应用例）：非 EACCES 的 `readdir` 失败（用 fd 耗尽构造 `EMFILE`，能力可探测）、非 ENOENT 的链接解析失败（自指链接构造 `ELOOP`）、**目录链接分支**的预算累计（5 个根内目录链接各 1200 项）。

变异回检（每一项都必须让该用例转红）：`N1` 去掉环重入防护、`N2` 去掉 `rel === ''`、`N3` 目录链接分支预算不共享、`N4` 链接解析失败一律跳过、`N5` 非权限 `readdir` 失败 fail-open —— **五项全部 pass 17 / fail 1**，没有恒绿断言。上一轮已回检的 `M1`／`M2`／`M2b`／`M3`／`M4`／`M4b` 亦全部转红。

夹具里两条能力探测在本机均生效（`# 目录权限在本机生效`、`# fd 耗尽在本机生效`）；不生效的环境只报诊断、不做对应断言，其余无条件断言仍在。

**附带观察（未作为断言，也未据此改实现）**：根内环存在时，SDK 自身会沿环重复发现同名技能（实测 17 条）。这是它自己的发现规则的产物，本片不复制也不改写它的规则；去重不在 C05 已确认要求内，因此只如实登记，不擅自扩大范围。

### 验收补证：`stat(real)` 失败处理器的公共路径证据

复核指出：`stat` 失败原先回落成 `() => true`（一律当目录），而当时的夹具**没有任何一条真正走到过这个处理器**——把普通目录递归删掉会让旧变异 M3 转红，只能证明"正常目录需要递归"，证明不了失败分支被调用。**该判断成立，本轮只收这一点。**

**实现改动**（`src/adapters/references/index.ts`）：

- 含糊回落换成**可辨原因**：`stat(real)` 失败时按 errno 分别处理——`ENOENT` 沿既定断链策略（目标读不到任何内容）跳过；`EACCES`／`EPERM` → `permission-denied`；其余（环路、句柄耗尽等）→ `unreadable`。两种失败都不再是"当作目录"，也不再含糊放行。
- 新增 `ReferencePortOptions.stat` 测试接缝（缺省即 `fs.stat`，正常路径行为不变），与 pi 会话的 `openStorage` 同一性质：只替换链接目标的 `stat`，用于注入可辨的元数据读取失败。不新增产品权限模式，也不引入任何原子／特权文件系统操作。

**受控证据**（同一个公开 `NodeReferencePort.list`，不改真实权限、不动账号）：

| 注入 errno | 期望可辨原因 | SDK 是否进入 |
|---|---|---|
| `EACCES` / `EPERM` | `permission-denied` | 否（0 技能） |
| `ELOOP` / `EMFILE` | `unreadable` | 否（0 技能） |
| `ENOENT` | 按断链策略跳过，其余技能照常可用 | 是 |
| 不注入（对照） | 无任何预审问题，技能照常可用 | 是 |

夹具额外钉住两件事，避免"验的是别处"与恒绿：注入点必须**真的被打到**（断言注入函数实际被以该目标路径调用，且比对用 `realpath` 后的真实路径——临时根在 `/var` 下而 `/var` 本身是符号链接，拿原串比会永远不相等）；根内另放一个**畸形技能**，SDK 一旦进入必然产生 `skills-unavailable` 诊断，因此"没有诊断"是有意义的断言，对照行则断言该诊断**确实出现**。

**红反例与回检**：

### P1-4 的真实界面验证方式（受控在途门禁）

这一项要求「用受控在途桥 + 真实组件／界面动作」验证，既不能用定时抢时序，也不能拿纯函数手传新 mode 当实路证据。三条通路的在途窗口都由**主进程门文件**掌握，与既有 `DCODE_TEST_SEND_RESULT_GATE` 同构：

- 新增 `DCODE_TEST_RECEIPT_RESULT_GATE`（`1`／`all`）：`checkReceipt` / `retrySend` 在**应用层真实完成后**，先写 `receipt-result-waiting-N`（含 `op`、`sessionId`、`blockId`），门文件出现前不把应答交给界面，写 `receipt-result-released-N`。回查与重试**各自计数、各自门文件**，可辨可分别放行。
- 回查／重试的门**同时扣住确认回执的那一次快照推送**。原因：这两条通路里，把消息块确认成 `accepted` 的是快照推送（`unknownOps` 效果据此清稿），只扣外层应答会造出「已到但续跑未跑」的假在途，用例就验不到真实在途。两处同门放行。
- 门标记一律**先写临时文件再 `rename`**：测试按文件出现判定在途，非原子写会让它读到半个 JSON（这一点是红反例回检时暴露的真实缺陷，见下）。
- 场景起点全部是产品自己会产生的状态，不手工改状态文件：直接应答用 `DCODE_TEST_SEND_RESULT_GATE=all`；查回用 `DCODE_MOCK_DROP_RECEIPT_ONCE=1`（执行端已接收并记录，只是给界面的回执待核对 ⇒ 原草稿与发送身份都在场）；重试用 `DCODE_MOCK_UNKNOWN_ONCE=1`（确认未接收 ⇒ 入口转为重试）。

场景里对「原身份」逐项留证：在途标记里的 `operationId`／`blockId` 必须与时间线上的原消息块一致，发送后原提交 `mode` 仍是 `steer`、`operationId` 不变，新用途只归当前草稿。

## 技能发现响应性实测（限定 9 后半）

`async`／`lazy` 外壳不作为证据，这里量的是**事件循环实际被占多久**。

### 上一版归因作废，原因

上一版写「分段计时……`loadSkillsFromDir` 30ms／延迟 0ms，**同步的 SDK 调用本身不是阻塞源**」。该结论不成立，两个方法问题：

1. 计时器在同步调用返回后**立刻** `clearInterval` 再读 lag —— 只观测到调用期间，调用结束后仍被饿死的定时器根本没被采到，lag 因此系统性偏低。
2. 拿「有上限规模冷 801ms／延迟 18ms」当成上限压住了稳态成本 —— 列表上限 `MAX_LISTED_PER_KIND = 200` 是**完整 SDK 扫描之后**才做的呈现切片，它既不限制此前的目录遍历，也不限制 SDK 内部读取。

### 修正后的采样方法

`/tmp/c-resp-attr.mjs`，`node --import tsx /tmp/c-resp-attr.mjs`（exit 0，raw `/tmp/c-resp-attr.log`）。采样器（名义 5ms）在**整个测量窗口持续运行**：窗口前 100ms、调用期间、以及**调用结束后 300ms**；每次记录「实际触发时刻 − 名义到期时刻」，相位标记打进同一时间线。归因只依据这个连续采样，不在调用返回时清表。

### 实测（300 技能 / 2000 文件，同一进程）

| 测量 | 总耗时 | 窗口内最大事件循环迟到 | 调用结束后 300ms 内最大迟到 | 返回 |
|---|---|---|---|---|
| ① 冷（进程内第一次 `list`，含 SDK 模块加载） | 1462ms | **245ms** | 1ms | 文件 200 / 技能 200 |
| ② 热（同一端口第二次 `list`） | 50ms | **22ms** | 1ms | 文件 200 / 技能 200 |
| ④ 小规模对照（1 技能 / 50 文件） | 2ms | 0ms | 1ms | 文件 50 / 技能 1 |

### 归因（据上表，不外推）

- 冷调确实**会**阻塞事件循环：窗口内观测到一次 245ms 的迟到，落在窗口末尾。该峰值与 E2E 里「第一次点「＋」时最慢一次 `getSnapshot` 往返 251ms」**量级一致**，两条独立采样指向同一处（进程内第一次加载 Pi SDK 模块）。但这是量级推断而非因果证明——脚本没有把模块加载与目录遍历分开计时，**不能据此断定整段峰值都归模块加载**。
- 调用结束后 300ms 内最大迟到 1ms —— 停顿不在调用之后的尾巴上，全部发生在调用窗口内。
- 稳态（热）是几十毫秒量级，最大迟到 22ms。
- **列表上限 200 不约束发现成本**：④ 与 ② 的返回**呈现量**都 ≤200，耗时却随被遍历／被扫描的量从 2ms 变到 50ms。真正给发现成本封顶的是**遍历条目上限 `MAX_ENTRIES = 4000`／深度 `MAX_DEPTH = 8`** 与技能审计的 `MAX_SKILL_AUDIT_ENTRIES = 4000／深度 6`，不是那个 slice。

### 取舍（普通工程选择，已自行收口）

启动期预取与否是本片内的常规实施选择，不作为需要外部裁定才能推进的停办项。理由已记：预取等于让所有用户每次启动都先付这份成本，包括从不使用引用的人；留在现状则代价落在用户第一次点「＋」时——两者上面都给了实测。本片按现状交付并如实登记这些有限实测，不编造帧预算，也不为此改动正常启动路径。
