# D Code 0.0.28 原生产品数据与多会话运行基础设施产品需求

状态：Implementation Candidate（实现候选；自动门禁与 Local Dirty Candidate 通过，干净候选、真实认证交接与原生人工验收待完成）

本 PRD 交付 `0.0.29` 任务工作台所需的完整基础设施：D Code Product Store、原生 Task / Session / Run 身份、Raw Input / Effective Input、Pi 单向导入、多 Runtime Supervisor、Coordinator / Child Agent 运行事实、D Code System Prompt 与 Active Tool Set。它不完成最终 UI/UX，但必须能通过当前 App 的兼容入口、结构化协议与诊断面真实运行和验收，不能只在单元测试中存在。

目标对象关系见[完整形态产品模型与交互契约](../20-产品与交互/0001-D-Code-完整形态产品模型与交互契约.md)，数据权威与 Pi 导入边界见 [ADR 0037](../决策档案/0037-D-Code-原生产品数据权威与-Pi-单向导入边界.md)，系统提示词与工具同源见 [ADR 0040](../决策档案/0040-D-Code-系统提示词与活动工具同源边界.md)。

## Problem Statement（问题陈述）

当前 `0.0.27` 可以保存、列出、搜索和依次打开多个 Pi Session，但不能同时运行多个会话。Host 只有一个活动 AgentSession；打开新会话会先关闭旧 Runtime，Prompt / Abort / State 也只面向“当前活动会话”。App 同样只有一个选中会话、一份流式状态和一个当前 Run，运行中切换会话会被拒绝。Pi SDK 能创建多个 AgentSession 实例，但 D Code 尚无负责多实例身份、生命周期、路由、隔离、恢复和产品呈现的 Supervisor。

D Code 的产品对象也仍没有独立事实源。Task、Coordination Session、Child Agent Session、Raw Input、Effective Input、Agent Run、Artifact 和 Evidence 只存在于目标文档或由 Pi 扩展间接表达；继续以 Pi JSONL 和当前 active Runtime 作为产品根，就无法让一个 Task 跨多个会话、多个模型和多轮执行保持同一身份。

模型同时仍可能接收 Pi 的通用身份、Pi 自动上下文和与真实 API Tools 漂移的工具说明。若先单独建立临时 Prompt 存储，随后再迁入 Product Store，会增加另一轮数据迁移和双权威风险。因此 `0.0.28` 必须一次建立 D Code 自有产品数据与多会话运行主干，并让 Prompt / Tool / Receipt 直接归属于该主干。

## Solution（解决方案）

### 1. D Code Product Store（D Code 产品数据仓）

D Code Product Store 成为下列对象的唯一产品权威：

- Project；
- Task、Task Goal、Acceptance、Plan、Work List 与 Work Item；
- D Code Session、Coordination Session、Child Agent Session 与 Session Path；
- Raw Input、Effective Input 与来源转换关系；
- Agent Profile、Session Run、Team Run、Agent Run 与运行时 Profile 快照；
- Artifact、Evidence、Finding、Request 与 Report；
- Runtime Environment、Active Tool Set revision 与 Effective Prompt Receipt；
- Pi Import provenance（导入来源证明）、恢复状态与用户关注态。
- Model Catalog、Provider / 模型选择、Capability Registry 与能力配置；
- Composer Draft、Follow-up Queue、归档、置顶、会话变更账本、自进化回执及现有 D Code 本机产品状态。

上述数据统一位于当前 macOS 用户的 `~/.dcode/` D Code Data Root。具体数据库文件、子目录和索引布局属于实现选择，但 Session、设置、Profile、Capability / Model 配置、受管 Artifact、日志与恢复资料不得继续分散到 Pi agent-dir 或多个无迁移合同的 App Support store。D Code Data Root 只能保存凭据安全引用与认证状态，API key、OAuth token 和认证文件正文继续使用 Keychain 或外部安全来源。

Project Directory 中的源码、普通文件与一等项目文档继续以文件系统为正文权威；Product Store 只保存类型、路径、revision、引用和加载记录，不复制正文建立竞争权威。

D Code Model Catalog、Credential Reference 与 Runtime Model Selection（未来运行模型选择）同样由 Product Store 负责。Pi Runtime 可以在首次迁入或受控发现时提供非敏感目录和外部认证桥状态，但 D Code 不再通过 Pi `settings.json` / `models.json` 写 Provider、默认模型或启用范围，也不通过 IPC 接收 API Key、OAuth 值或 Pi 认证交互输入。启动 Runtime 必须先核对 Product Store 中的目录、选择和已配置安全引用，再将选择显式应用给 Adapter；选择只影响未来 Runtime，不热改在途 Run。

Product Store 必须使用版本化 schema、稳定对象 ID、原子事务、单写入所有者、幂等请求 ID 和可恢复迁移。损坏、未知 schema version 或事务结果未知时保留原字节并停止覆盖，不得回退为空成功。索引和投影均可从权威记录重建。

首次迁入 `~/.dcode/` 是单向 schema promotion。迁移提交前必须完成来源快照、完整校验和备份；任一步失败都不得提交 Product Store，也不得启动会写入新 schema 的 D Code。事务提交成功并开始产生新 Task / Session / Run 后，不支持降级回 `0.0.27`。旧 Store 只读保留用于核对和紧急数据修复，不能继续双写，也不承诺旧 App 能读取 0.0.28 之后的数据。

`0.0.28` 必须把当前分散在 `~/Library/Application Support/D Code` 与配置所指 `agentDir/pi-dcode` 中的 Project、草稿、Queue、关注态、归档、置顶、变更、Evidence、自进化、禁用包、模型与能力配置迁入 `~/.dcode/` Product Store，保留稳定身份、顺序、revision 和失败状态。迁移按来源逐项原子核验；单项成功后旧 store 转只读，确认 App / Host 都已切换消费者后退出。不得长期双写，也不得让 `0.0.29` 继续读取旧 store 补齐 Product Store 缺失事实。旧 Session Lease / lock、在途进程状态和可重建搜索缓存不迁移：升级前先安全关闭，随后在新 Runtime Root 重建。凭据只迁移安全引用与认证状态，不复制正文。

升级时，当前已经由 D Code 管理并出现在 Recent / Project 中的 Pi Session 自动接管：有且只有一个既有 Project 归属时，在该 Project 下创建一条 Legacy Task；没有明确 Project 时，在 User Scope 下创建 Legacy Task。每条旧 Pi Session 初始转换为一个 Task，并把转换后的首个 D Code Session 指定为 Coordination Session，同时建立 Coordinator assignment；关联 Draft、Queue、归档、置顶、Attention、Changes、Evidence 与恢复状态在同一事务中迁移，源 JSONL 保持只读。该自动接管只服务已经进入 D Code 产品范围的资产，不扫描并导入整个 Pi agent-dir。

### 2. User Scope / Project Scope → Task → Session / Run 原生关系

- Project 是长期容器；Task 是基本完成单位，并必须恰好属于一个 Project Scope 或当前用户的 User Scope。创建 Task 保存短期目标、范围、停止边界与验收，但不会仅因创建而启动模型。
- 未选择 Project 的 Task 不使用 null owner，也不显示成“未选项目”：它属于 User Scope，由 User Home 组织，默认执行目录映射为当前 macOS 用户 Home Directory；Task、Session、Draft、Artifact 与设置数据仍写入 `~/.dcode/`，不会散落到 Home Directory 普通文件中。
- 每个新 Task 建立一个 Coordination Session 和稳定 Coordinator assignment（协调者指派），作为用户默认任务对话；Task 可以再拥有零个或多个普通或 Child Agent Session。保存 Task 或 Session 本身不会常驻启动模型进程。
- Host 必须提供按 D Code Session ID 的只读 Session Presentation（会话呈现）与精确 Prompt 路由：查看只读取 D Code Session、可选 Adapter binding 和当前 Runtime，不抢占 Pi Session；首次向 Coordination Session 提交时由 Host 从其 Task Scope 派生 Runtime，Child Agent Session 只在其自身 Agent Run 已活动时接收用户消息，禁止按标题、cwd 或全局 active Session 猜测目标。
- Product Store 提供稳定 Agent Profile 实体，至少建立 Coordinator、Explore、Worker、Verifier 四个可编辑内置档案，并支持创建、读取、更新、停用与版本化。Agent Run 保存启动时快照；后续 Profile 修改只影响未来 Run，不热改在途成员。
- 用户首次向 Coordination Session 提交执行输入或显式开始团队执行时，创建一个 Coordinator Agent Run。该 Run 可以跨多个 Session Run；用户先与协调者沟通后再启动 Team 时，Team 必须复用同一 Coordinator Agent Run / Runtime 或在其空闲边界明确拒绝，不能为同一 Coordination Session 创建第二个并发写入者。它记录 Profile 快照、实际模型、角色、状态与回执；暂停、等待或进程消失不删除 Coordinator assignment。
- Coordinator Agent Run 可以创建一轮 Team Run，并在其中派发一个或多个 Child Agent Run。`0.0.28` 同一 Task 同时最多一轮 active Team Run；一轮收口后可以开始下一轮。每个 Child Agent Run 关联任务包、实际模型、执行目录、Active Tool Set、Child Agent Session、状态、报告与证据。
- 首个基础闭环必须支持一个 Coordinator 与至少两个 Child Agent；两个成员可以串行或并行运行，并以结构化 Finding、Request、Report、Artifact 与 Evidence 回报。
- Coordinator 可以维护 Plan / Work List、处理成员请求和综合报告，但不能替用户接受 Task。Agent Run 完成、Team Run 收口和 Task 验收分别成立。

### 3. Raw Input（提交原文）与 Effective Input（生效输入）

- 用户提交的逐字文字、附件引用和来源事实形成不可变 Raw Input。Skill 展开、命令转换、上下文组装、摘要或编辑重走不得覆盖它。
- Effective Input 引用来源 Raw Input，并记录 Task 合同、能力调用、选择的 Context Projection、转换版本与附件来源；模型真正接收到的输入可以重建和解释。
- 编辑并重走或从历史继续会产生新的 Raw Input、Effective Input 和 Session Path 关系，原事实始终保留。
- Raw Input、Effective Input、Session Run、Effective Prompt Receipt 与模型结果必须拥有稳定关联；任一写入失败不得留下无法归属的消息或 Run。

### 4. Pi Session Import（Pi 会话单向导入）

- 其他 Pi Session 只能通过用户点击显式“导入为任务”按钮进入 D Code；发现、搜索或预览不会自动导入。
- 每次导入创建一个新的 D Code Task，并把转换后的首个 D Code Session 指定为该 Task 的 Coordination Session，同时建立 Coordinator assignment。用户必须选择 Project Scope 或 User Scope；选择 User Scope 时默认 cwd 为用户 Home Directory。首版不把 Pi Session 静默追加到既有 Task。
- 导入读取源 JSONL、保留源 ID / 路径 / digest 与转换证据，但不修改源文件；发布目标前在单个 Product Store 事务内完成校验和写入。
- 同一来源与同一导入版本重复请求必须幂等返回既有结果，或要求用户明确创建另一份副本；不得静默生成不受控重复会话。
- 导入后的会话使用 D Code 身份独立续写，不双写、不持续同步，也不承诺导出后可由 Pi CLI 继续使用。首次及后续续写从 Product Store 当前 Session Path 派生有界、二次脱敏的 Imported History Projection（导入历史投影）进入 D Code System Prompt；该历史明确是外部证据、不是当前指令或 D Code Raw Input，正文不进入 Receipt、Raw Input 或 Effective Input，也不重新读取源 Pi JSONL。
- 导入失败、进程中断或未知结果不能发布半个 Task / Session；源 Pi Session 始终保持原样。
- Pi 历史消息保留原文本、条目 ID 与来源证明，但旧 Pi 记录无法证明“用户在 D Code 提交前的逐字 Raw Input”或其转换链；导入时必须把 lineage status 标记为 unknown，不倒填为 D Code Raw Input / Effective Input。导入完成后的新提交才使用完整 Raw / Effective 合同。

### 5. Runtime Supervisor（运行时监督器）

Runtime Supervisor 取代单一 active Runtime，按稳定 Runtime ID 管理多个 Agent Runtime Adapter 实例。每项运行请求与事件必须显式携带 Task Scope 判别联合、Task、D Code Session、Session Run、Agent Run 和 Runtime 身份：User Scope 使用 `scopeKind=user + userID`，Project Scope 使用 `scopeKind=project + projectID`；Project ID 只在 Project Scope 出现，不能以 nullable Project 表达 User Scope，也不能依赖全局“当前会话”。

- 不同 D Code Session 可以同时保持活动并真实并行执行；切换当前查看会话不会关闭、Abort 或暂停后台 Runtime。
- 同一 D Code Session 同时最多一个可写 Session Run；第二个写入请求必须等待或明确失败，不能并发改写同一会话事实。
- 同一可写工作目录同时最多一个 Agent Run。Declared Capability Scope 不是技术权限边界：Active Tool Set 只要包含写文件、任意命令、可能改动工作区的 Provider 工具或无法证明只读的工具，该 Run 就一律按可写处理，并必须使用独立且已验证的 worktree 或等价隔离目录。只有全部工具均可证明只读的集合才可共享来源；下一 Run 若升级为可写工具集，必须先分配并核验隔离目录，否则拒绝启动。
- 每个 Runtime 拥有自己的 AgentSession、Prompt / Queue / Steer / Abort、结构化等待、工具调用、模型设置、事件序列和失败状态。某一 Runtime 等待用户、失败或停止不得阻塞其他 Runtime。
- Runtime 数量、并发模型请求和 retained workspace（保留工作空间）必须有明确上限与资源回收；达到上限时排队或诚实拒绝，不静默杀死现有运行。
- Host 重启后恢复 Task / Session / Run 关系、最后持久状态、报告、Artifact、Evidence 与未处理工作空间；已经消失的模型生成、工具调用和进程标记为 interrupted（已中断）或 unknown（结果未知），不伪装继续运行，也不自动重放外部副作用。

### 6. D Code Prompt Assembler 与 Active Tool Set

每次 Session Run 启动 Agent Loop 前，D Code 从 Product Store 与当前 Runtime 事实组装 Effective System Prompt：

1. D Code Identity；
2. User / Project Scope、Task、Session、Agent Run、cwd / worktree、模型与模式等 Runtime Environment；
3. Coordinator、Explore、Worker、Verifier 或其他真实 Agent Role Contract；
4. Active Tool Manifest；
5. 强制 `AGENTS.md` 与已选择一等项目文档 / Knowledge 引用组成的 Context Projection；导入会话另可包含其当前路径的有界 Imported History Projection。

Prompt 完整替换 Pi 默认身份、Pi 文档入口、Pi 自动 Skill catalog、Pi project context、Pi cwd footer、未经归一的 promptGuidelines 与未经选择的 SYSTEM / APPEND_SYSTEM；cwd 只能由 D Code Runtime Environment 产生一次。

Runtime 内置、已适配扩展、D Code 自有与 Provider 工具必须先归一、过滤并冻结为当前 Run 的不可变 Active Tool Set。模型 API Tools 与 Active Tool Manifest 只能从该集合生成，工具名集合完全一致，并复用同一 canonical model-facing description；缺 schema、缺执行器、未启用或 Provider 不支持的工具两侧都不出现。

Effective Prompt Receipt 直接写入 Product Store。执行顺序固定为“冻结 Prompt / Tools → 在同一运行事务中原子持久化 Effective Input、Session Run 与 Receipt → 发出 Provider 请求”。持久化失败、损坏、未知版本或工具不一致时保留原事实并阻止请求，不回退到 Pi Prompt 或无回执运行。Receipt 只证明准备使用的系统输入，不证明 Provider 接受或 Run 完成。

每次 Provider 请求、工具调用或外部副作用都必须使用独立稳定 Attempt ID，并遵循“先写意图、再执行、后写结果”：执行前持久化所属 Task / Session / Run、操作类型、目标身份、脱敏参数摘要与 replay policy；执行后追加 Outcome、Tool Result / Provider Response 引用和完成时间。进程在执行与结果落盘之间退出时，Attempt 保持 unknown，Foundation Console 必须能核对具体哪次操作可能已发生；unknown Attempt 禁止自动重放，除非后续独立合同能证明幂等且由用户显式选择。

### 7. Context Projection 与项目哲学来源

- 每个 Agent Run 建立及每个 Session Run 启动前解析当前作用域适用 `AGENTS.md`；工作目录变化只影响下一 Run，不热改当前回执。
- D Code 识别根 README、PRODUCT、DESIGN、GLOSSARY、doc map、精确 PRD 与 ADR 的类型、路径、revision 和加载状态；其他文档按 Task 需要读取，不默认全文注入。
- 每个 Task 拥有 revisioned 的显式 Context Selection：`AGENTS.md` 强制加载；Scope Document 以 Task cwd 的相对具体文件选择，Global Knowledge 以当前 User Home 下显式根目录的具体文件选择。目录、`..`、符号链接与未经选择的 Pi project context 都不得成为隐式来源；选择失效或含凭据时在 Pi Session / Provider 副作用前拒绝本次 Run。
- PRODUCT / DESIGN 缺失、不是普通文件或不可读取时如实记录；可以列出有界分散依据路径，但不得自动合并、生成或宣布一份新的产品哲学权威。
- `0.0.28` 只建立 Project Constitution 与有界 Knowledge 引用接缝，不完成全局 Content Vault、Vision 或自动上下文抓取。
- Effective Prompt Receipt 只保存模板 / Prompt hash、来源身份、路径与 revision，不复制 System Prompt 或一等文档正文。来源仍可由 Git revision 或其他版本化事实找到时可以回查；未提交、后续被改写或已不可寻址的历史正文明确显示 unavailable，产品只承诺核对当时 hash 与来源，不声称完整重建。

### 8. 为 `0.0.29` 提供结构化投影

Product Store 与 Runtime Supervisor 必须通过结构化协议提供：

- Task 目标、状态、Plan、Work List、验收与用户关注态；
- Coordination / Child Session 树及当前选择；
- Team Run / Agent Run 的角色、模型、状态、活动、等待请求、报告与执行目录；
- Artifact、Evidence 与 Report 引用；
- Runtime Environment、Context Projection、Active Tool Set 与 Effective Prompt Receipt；
- 每条实时事件的 Task / Session / Run / Agent / Runtime 身份。
- Agent Profile 列表、版本、启用状态与运行快照；
- Pi Import Candidate 列表、来源预览、转换状态与导入结果；
- Composer Draft、Follow-up Queue、模型选择与 Provider / Capability 状态；
- Provider / Tool / External Side-effect Attempt 及 Outcome / Result 引用。
- Task Context Selection 的当前 revision、具体来源和每次 Run 的只读 Prompt Source 状态。

同时必须提供供 `0.0.28` 最小控制面和 `0.0.29` 正式工作台共同使用的结构化 mutation contract（变更合同）：

- 创建 / 更新 Task、Goal、Acceptance、Plan 与 Work Item；
- 以 Task / Scope / Store / Context revision 和 request ID 原子替换有序 Context Selection；
- 创建 / 更新 / 停用 Agent Profile；预览 Pi Import Candidate 并执行 importAsTask；
- 保存 / 清空 Composer Draft，提交 Raw Input，增加 / 编辑 / 排序 / 撤回 Queue Item；
- 开始 / 暂停 / 继续 Coordinator 或 Team Run；
- 派发 Child Agent、回答 Request、停止 / 重试单个 Agent Run；
- 对明确 Session Run 执行 Steer / Abort，更新未来 Run 的模型 / Provider / 推理选择；
- 要求返工、提交综合 Report、接受 / 拒绝 Task 验收；
- 选择 / 恢复 Session、处理 Artifact / Evidence 与用户关注态。

每个变更请求必须带明确 Task Scope 联合、Task / Session / Team Run / Agent Run 目标、expected revision、幂等 request ID 和调用来源；结果返回新 revision、受影响对象与结构化事件。目标漂移、revision 冲突或结果未知时不得猜测成功。`0.0.29` 只能调用这些合同，不能直接修改 store 或再发明 UI 私有命令。

`0.0.29` 不得解析聊天文案来猜进度、成员、等待事项或交付物。`0.0.28` 必须在当前 App 中提供最小可操作 Foundation Console（基础设施控制面），使用户可以创建 / 编辑 / 选择 Agent Profile，预览 Pi Session 并点击“导入为任务”，创建 / 选择 Task、启动 Coordinator + 两个成员、切换观察 Session / Run、回答结构化请求、停止单个成员、核对 prepared / unknown Attempt、查看 Report / Artifact / Evidence 与执行 Task 验收。它可以沿用当前布局和诊断式呈现，但必须调用与 `0.0.29` 相同的 query / mutation contract，不建立临时 UI 私有状态；不能只靠测试脚本使用。

## User Stories（用户故事）

1. 作为 D Code 用户，我希望一项 Task 可以同时拥有协调会话和多个子会话，从而不必等待一个会话结束后才能开展独立调查与实现。
2. 作为没有选择 Project 的用户，我希望 Task 仍明确属于自己的 User Scope、默认在 Home Directory 工作，并由 `~/.dcode/` 统一保存会话和设置，而不是成为无归属对象。
3. 作为协调者，我希望向两个成员派发有界任务、分别观察状态并接收结构化报告，从而在不共享私有上下文的情况下综合结果。
4. 作为长期项目维护者，我希望 Raw Input、Effective Input、Prompt、工具、报告和证据都能追溯到同一 Task / Run，从而在重启和返工后仍知道事实来源。
5. 作为既有 Pi 用户，我希望把历史会话一次性导入 D Code 并继续工作，同时确保源 JSONL 不被修改或双写。
6. 作为下一版界面的实现者，我希望直接读取 Task、会话树、Run、等待事项和 Artifact 的结构化投影，而不是从模型回复猜测产品状态。

## Confirmed Constraints（已确认约束）

- D Code Product Store 是本版新增产品状态的唯一权威；不建立临时 Prompt Store、第二任务库或与 Pi JSONL 双写的中间权威。
- 当前用户的 D Code 产品数据根固定为 `~/.dcode/`；Project 文件正文不迁入，凭据正文不明文落盘。不同 macOS 用户的数据与设置互相隔离。
- Provider 配置迁移只接管目录、模型、设置、认证状态与 Keychain / 外部安全引用；迁移后必须通过真实认证交接完成请求。引用失效时明确要求重新认证，不把空目录、匿名失败或旧 Pi 凭据存在伪装成可用。
- Task owner 是 Project Scope 或 User Scope 的必选联合关系；User Scope Task 默认 cwd 为用户 Home Directory，但 Home Directory 与 `~/.dcode/` 分别承担工作文件和产品数据职责。
- Pi SDK 继续作为首个 Agent Runtime；本版利用其多 AgentSession 实例能力，不重写 Agent Loop，也不接入第二 Runtime。
- 同一 Session 单写入、同一工作目录单写入、隔离 worktree、显式 Runtime 路由与外部副作用不盲重试是硬边界。
- 用户原始提交、模型实际输入、系统 Prompt、API Tools、模型回复、工具结果和产品状态分别持久化与呈现，不互相冒充。
- 凭据正文、环境变量值、隐藏 Thinking 与不必要的项目正文不得进入 Product Store、Prompt Receipt、IPC、日志或普通界面。
- 扩展是能力来源，不是产品兼容面；D Code 可以复用实现，但拥有对象、状态、生命周期、Agent 接口与原生呈现合同。
- 当前文件系统与 Git 是代码和项目文件事实；Session Path、Product Store 或 Agent Run 不承担代码快照与回滚。
- 实现、自动测试、真实多 Runtime 验收、UI/UX 验收、候选构建、commit、tag 与发布继续分别成立。
- `0.0.28` Product Store 晋升提交后不支持降级运行 `0.0.27`；迁移前备份只用于数据修复。Self-build 的普通候选回滚合同不得被解释为跨该 schema 边界的数据降级。

## Acceptance Criteria（验收标准）

### Product Store 与输入事实

- [ ] 全新用户只在 `~/.dcode/` 建立 D Code Product Store、Session、设置、Profile、能力 / 模型配置、受管 Artifact、索引、日志和恢复资料；Project 文件保持原位，凭据正文不进入该目录。
- [x] Task 创建时必须选择 Project Scope 或自动进入 User Scope；不存在 null owner 或“未选项目”伪 Project。User Scope Task 默认 cwd 为当前用户 Home Directory，产品数据仍只进入 `~/.dcode/`。
- [ ] 重启后可以恢复一个 Project、一个 Task、一个 Coordination Session、两个 Child Agent Session、对应 Team / Agent / Session Run、Plan、Work List、Artifact、Evidence 与未处理报告，稳定 ID 和关系不变。
- [x] Plan / Work List 已成为 Product Store 原生事实：Plan 保留 superseded 历史，Work Item 保留稳定 ID、状态、归属、详情与顺序；创建、更新、重排和重启后读取均使用 revision / request ID，不从会话文案重建。
- [ ] Raw Input 逐字不变；每个 Effective Input 都能回到来源 Raw Input、转换版本、Task 合同、附件和 Context 来源。编辑重走不会覆盖原事实。
- [x] Product Store 使用版本化 schema、原子事务、幂等请求与单写入所有者；写失败、损坏、未知版本或结果未知时保留原字节、不发布半成品，也不回退为空成功。
- [x] Product Store 支持 v1 → v2 单向 schema promotion：先在 `~/.dcode/migrations/` 写入私有前备份，再原子建立 Task Context Selection；每条存量 Task 获得空集合，失败不发布半个 schema，成功后不支持降级或双写。
- [x] 首次迁移在事务提交前任一故障都保持旧 Store 字节不变且新版本不开始写入；提交成功后旧 Store 只读、无双写，尝试以 `0.0.27` 继续运行会得到明确“不支持降级”提示，而不是打开陈旧数据。
- [x] 现有 Project、Draft、Queue、Attention、Archive、Pin、Changes、Evidence、Self-evolution、Model / Capability 配置逐项迁入 Product Store；迁移前后身份、顺序和 revision 一致，旧 store 退出写入后没有双写或旧消费者。
- [x] Product Store 投影 D Code Model Catalog、Credential Reference 与 Runtime Model Selection；未来 Runtime 只接受该选择并显式设置对应 Adapter 模型。旧 Pi 设置 / `models.json` 写入和 Pi 认证值 IPC 路径明确拒绝，凭据正文不进入 Store、Receipt、日志或 Swift 输入。
- [ ] 至少一个升级前已认证 Provider 在安全引用迁移后能完成真实模型请求；Product Store、IPC 与日志不含凭据正文。失效引用显示“需要重新认证”并保留其他可用配置，不出现空成功。
- [x] 当前已由 D Code 管理的 Pi Session 自动转换为一条 Legacy Task，其首个 D Code Session 是 Coordination Session 并带 Coordinator assignment：唯一 Project 归属得到保留，无明确 Project 时进入 User Scope；关联本机状态同事务迁移，源 JSONL 不变，未进入 D Code 的 Pi Session 不被扫描导入。

### Pi 单向导入

- [x] 其他 Pi Session 只有用户点击“导入为任务”才进入 D Code；用户选择 Project Scope 或 User Scope 后，原子创建新 Task、Coordinator assignment 与作为 Coordination Session 的首个 D Code Session，源路径、ID、digest 和转换证据可回查，源 JSONL 字节不变。
- [x] Pi 历史用户消息保留文本与 provenance，但 Raw / Effective lineage 标记为 unknown，不倒填成 D Code 提交原文；只有导入后的新输入具有完整 Raw / Effective 关系。
- [x] 相同来源和导入版本重复请求不会静默产生重复会话；导入中断或失败不发布半个 Task / Session。
- [x] 导入会话可以在 D Code 中独立续写：Provider 只接收新提交作为 user input，系统上下文使用当前路径的有界、二次脱敏 Imported History Projection；源 Pi JSONL 的 digest 前后不变，Raw / Effective Input 只记录导入后的新提交。

### 多 Runtime 与并发

- [x] 同一 Host / App 内，一个 Coordinator 与至少两个 Child Agent 使用三个独立 AgentSession；两个 Child Provider 请求存在真实时间重叠。
- [ ] 切换当前查看的 Session 不关闭、Abort 或暂停其他 Runtime；一个成员等待用户时，另一个成员仍能继续并完成。
- [x] Prompt、Queue、Steer、Abort、等待输入、模型设置和事件都按显式 Session / Run / Runtime 身份路由；操作单个成员不会误作用于其他成员。
- [x] User Scope 与 Project Scope 请求 / 事件都携带非空的 Task Scope 判别联合；User Scope 不需要 Project ID，Project Scope 必须携带 projectID，null Project 不能通过协议校验。
- [x] 同一 Session 的第二个可写 Run 被等待或明确拒绝；两个写入成员不能共享同一工作目录，隔离失败时不启动。
- [ ] bash、命令别名、Provider 工具、符号链接解析和下一 Run 工具集升级均进入写入隔离判定；只有可证明全工具只读的成员可以共享来源，声明“只读”本身不能绕过。
- [ ] 达到 Runtime / Provider 并发上限时状态可辨认，既有运行不被静默终止；资源回收不会删除仍有关联 Task / Run 的工作空间或报告。
- [x] Host 重启后在途 Runtime 被标为 interrupted 或 unknown；不自动重放工具和外部副作用，也不伪装恢复模型进程。
- [ ] Provider 请求、每个 Tool Invocation 与外部副作用在执行前都有耐久 Attempt；执行后追加 Outcome / Result 引用。故障注入覆盖发送前、发送后和结果落盘前三个中断点，最后一种保留具体 unknown Attempt 且不会自动重放。

### Coordinator 与结构化回报

- [x] Product Store 至少提供 Coordinator / Explore / Worker / Verifier 四个稳定、可编辑、可停用的 Agent Profile；Agent Run 保存启动快照，修改 Profile 不改变在途或历史运行。
- [x] 新 Task 拥有稳定 Coordinator assignment 与 Coordination Session，但不因保存对象启动模型；首次执行创建 Coordinator Agent Run，一轮 active Team Run 收口前不能启动第二轮。
- [ ] Coordinator 可以显式派出两个成员、接收 Finding / Request / Report / Artifact / Evidence，并形成综合报告；成员完成不会自动完成 Task。
- [x] 子成员只获得有界 Task 包、适用规则和声明 Context；父子关系不共享会话内存，也不复制完整主会话历史。
- [ ] 用户可以回答某一成员请求、停止单个成员或接受 / 拒绝综合结果，而不影响其他成员运行。

### Prompt、工具与项目规则

- [x] 捕获到的每个最终模型请求只有 D Code 身份和对应 Agent Role，不含 Pi 默认身份、自动 Skill / project context / cwd footer、未经归一 guidelines 或未经选择的 SYSTEM / APPEND 内容。
- [x] 每个 Run 的 API Tools 与 Active Tool Manifest 名称集合完全一致，并关联同一 Active Tool Set revision；工具缺失或不一致时 Provider 不收到请求。
- [x] Effective Input、Session Run 与 Effective Prompt Receipt 在 Provider 请求前原子持久化；持久化失败时没有无回执 Run，也没有模型请求。
- [x] `AGENTS.md` 作用域、项目文档来源、环境事实和工具变化只在下一 Session Run 生效，旧 Receipt 不被覆盖。
- [x] Task Context Selection 只加载 `AGENTS.md` 加显式选择的具体 Scope Document / Global Knowledge 文件；来源、顺序与 Context revision 写入 Effective Input / Prompt Receipt。用户选择的来源不可读、越界或含凭据时，Host 在 Pi Session 绑定和 Provider 请求之前拒绝运行。
- [x] Worker 的 Scope Document 必须能由冻结 Git revision 物化到受管 worktree；忽略、仅本机或符号链接来源不会创建 worktree、Pi Session 或 Provider 请求。
- [x] Receipt 不保存完整 Prompt 或项目正文；来源内容后续变化时，Agent Environment 能区分当前匹配、hash 不匹配与历史正文不可用，不把 hash / path 冒充可重建全文。
- [x] Imported History Projection 在 Prompt 中被明确标注为外部历史证据、非当前指令、非 Raw Input；Prompt / Effective Input / Receipt 只持久化其有界元数据、digest、脱敏与截断事实，不持久化正文、隐藏 Thinking、工具参数或工具结果。

## Eval Scope（评测范围）
