# D Code 0.0.5 后续消息队列产品需求

状态：Release Candidate（发布候选；自动门禁与定向 Composer 界面验收通过，其余人工场景未执行）

本 PRD 冻结 `0.0.5` 的新增范围与验收边界；队列所有权和派发转换以 [ADR 0011](../决策档案/0011-后续消息队列所有权与派发边界.md) 为准，新会话的延迟创建以 [ADR 0014](../决策档案/0014-新会话延迟创建与本地草稿边界.md) 为准。`v0.0.4` 的唯一会话主页面、按需文件标签、三栏工作台、Session / Path、Composer Draft、会话观察与按需写入继续作为回归基线。

## Goal（目标）

让用户在当前 Agent 仍运行时继续写下下一步，并以可见、可管理、可恢复的顺序交给同一 Pi Session / Session Path；当前 Run 不被打断，尚未派发的意图不被冒充为会话消息，异常恢复不会静默丢失或重复发送。

同时修正新会话的事实边界：进入空白 Composer 只是本地草稿导航，首次提交非空正文时才创建真实 Pi Session，未输入就离开的用户不再留下空会话。

本版成立后，D Code 从“每一轮必须等完才能继续表达”变为“同一工作路径内可以连续安排下一条普通文本”。它仍不是后台任务系统、跨 Session 调度器或完整运行控制台。

## Problem（问题）

- 当前 Session Run 执行期间 Composer 的输入与发送被禁用，用户必须等待、打断当前工作，或把下一步临时记在 D Code 之外。
- 仅启用 Pi Runtime 的内存 `followUp` 无法支持逐项编辑、重排、撤回、跨重启恢复和稳定幂等，也无法为原生界面提供可信状态。
- 如果过早把排队正文写入 Pi Session，它就已经成为会话历史；如果只留在内存，崩溃或重启又会丢失。产品需要明确的派发前所有权和可验证的转移点。

## Scope（范围）

### 0. 新会话延迟创建

- 全局或 Project 内点击“新建会话”只打开绑定规范 `cwd` 的本地会话前草稿；此时没有 Session ID、Pi JSONL、来源标记、Lease、Recent / Project / Search 条目，也不调用 `session.create` / `session.open`。
- 空白或只有空白字符的草稿不写入本机资料；离开、取消或退出后直接消失。非空正文使用既有原子草稿资料保存，再次新建时恢复，仍不进入 Pi 会话、模型 Context 或搜索。
- 同时只保留一个会话前草稿。已有非空草稿时从其他目录再次新建，恢复原草稿并说明原因；发送或显式取消后才可为另一目录开始草稿。
- 首次提交非空普通文本时才调用 `session.create`。创建提交后立即进入 Recent，把输入转移到新 Session 的 root Path 草稿，再以 writable `session.open` 与 `session.prompt` 发送。
- 创建失败时保留会话前草稿且不产生 Pi Session；创建成功但打开或首次发送失败时保留真实空 Session 与其逐字草稿，明确提示重试，不自动删除或伪装成未创建。
- 会话前草稿页面沿用唯一 Conversation 主页面，不显示“对话”标签和信息检查器；顶部显示“新会话”，正文说明发送后才创建 Pi Session，并提供明确取消动作。模型、思考强度、极速、Context、命令、路径与 Follow-up Queue 在真实 Session 打开前不可操作。

### 1. 入队与可见性

- 当前没有活动 Run、没有尚未完成所有权转移的 Queue Item，也没有等待用户输入或权限决定时，普通非空文本继续沿用 `v0.0.4` 的直接发送路径，不额外制造单项队列。
- 当前 Run 正在执行且未等待用户输入或权限决定时，用户对普通非空文本执行发送动作，会先创建绑定当前稳定 Session ID 与 Path Lineage Anchor（路径谱系锚点）的 Queue Item。锚点是当前路径上的稳定 Entry ID，不是会随本轮消息追加变化的叶节点。只有本机原子保存成功后 Composer 才清空；失败时原草稿逐字保留并说明原因。
- 只要当前身份仍有待派发、暂停或结果未知的项目，新的普通文本就加入同一队列，不能绕过队首走直接发送路径；等待用户输入或权限决定的专用回复继续由原请求界面处理，不被普通队列截获。
- Composer 附近显示最小队列入口与待派发数量；展开后按实际顺序显示每项正文和状态。待派发项不得出现在 transcript、会话导航尺、搜索结果、模型 Context 或 Pi JSONL 中，也不得使用“已发送”“执行中”等文案。
- 队列表面不得恢复“对话”标签、独立右栏任务面板或新的固定工作区；唯一会话主页面与 `0.0.4` 的按需内容标签保持不变。

### 2. 派发前管理

- 每个 Queue Item 具有稳定且不可复用的身份。默认顺序为先进先出；用户可查看完整正文、编辑、调整顺序或撤回任一仍为待派发的项目。
- 编辑、重排和撤回必须原子保存，并提供键盘与 VoiceOver 等价操作。成功操作不改变当前 Run、Pi Session、Session Path、Composer Draft 或其他队列项身份。
- 一项进入派发转换后立即锁定，不再接受编辑、重排或撤回；界面显示“正在派发”或“结果未知”等真实状态，不能在派发与编辑之间静默竞争。

### 3. 顺序派发与所有权转移

- 当前 Run 只有在 Host 能证明正常收口、没有活动生成或工具、没有等待用户输入或权限决定时，才触发下一项派发评估。单独收到 `agent_end`、连接断开、失败或中止事件均不构成正常收口。
- 派发前再次核对 Queue Item 绑定的 Session ID、Path Lineage Anchor、当前可写身份与 Session Lease 条件。当前 Run 及同一队列已确认产生的唯一后继可以推进锚点；用户选择兄弟路径、从旧消息另起路径、外部写入或来源不明的叶节点变化都会暂停，不把消息静默送入另一条路径。
- 每次只派发队首的一项。Host 通过既有 Pi SDK Prompt 路径写入；Queue Item ID 稳定关联 Prompt ID。只有收到同一 Session ID、Prompt ID 与持久化用户 Entry ID 的匹配证据后，该项才从“D Code 待派发意图”转换为“Pi Session 普通用户消息”。
- 一项的 Pi 持久化确认不等于其 Agent Run 成功完成。该 Run 正常收口后才能评估下一项；若它失败、中止或进入等待态，剩余项目保留并停止自动派发。
- 实现必须声明有限的单项正文、单队列项目数与本机总字节上限，并以测试常量固定。到达上限时只拒绝新的入队或扩容操作，逐字保留原草稿与全部既有项目，不截断、覆盖或自动删除用户正文。

### 4. 暂停、恢复与未知结果

- 当前 Run 失败、中止、等待用户输入、等待权限、Host / Lease 中断、外部写入冲突、Session / Path 身份漂移或派发结果未知时，队列保持原顺序并停止自动派发；产品说明停住原因和安全下一步。
- 用户切换 Session 或 Path 时，原队列继续绑定原身份且不在新位置派发。返回原身份后，普通暂停可以由用户显式继续；“派发结果未知”必须先核对，不能以再次发送作为恢复手段。
- App 或 Host 重启后恢复全部尚未完成所有权转移的 Queue Item、顺序、绑定身份与派发状态。已取得匹配 Pi 持久化证据的项目不重新入队；不能证明结果的项目保持未知并阻止后续自动派发。
- 队列 Store 损坏或版本不支持时保留原始字节，禁用新增、编辑和自动派发并显示恢复入口；普通会话观察、历史阅读、文件预览和其他安全能力继续可用。Store 写入失败不得修改 Pi JSONL。

### 5. `0.0.5` 界面边界

- 队列入口、数量、顺序与管理动作都位于 Composer 附近，并复用既有会话页面的视觉层级；没有队列且 Run 空闲时不常驻空面板。
- 当前 Run 只需提供判断“仍在运行 / 已正常收口 / 已暂停派发”所需的最小反馈。会话栏 Activity View、完成关注态，以及当前活动、队列、等待输入、停止和重试的完整统一状态机与 Interaction Dock 排在 `0.0.6`。
- 队列状态不能只靠颜色表达；图标、文案、焦点、键盘顺序、Reduce Motion 与 Increase Contrast 下都应可辨认。

## User Stories（用户故事）

1. 作为正在等待 Agent 修改文件的用户，我希望继续输入“完成后再运行测试”，而不打断当前工具执行。
2. 作为连续补充要求的用户，我希望看到两三条后续意图的真实顺序，并在派发前修正文案或调整先后。
3. 作为改变主意的用户，我希望撤回尚未派发的一项，而不影响当前 Run 和其他队列项。
4. 作为遇到失败、权限询问或 Host 中断的用户，我希望队列停住并保留，而不是在我不知情时继续发送。
5. 作为重启 D Code 的用户，我希望恢复原队列，并确信已经进入 Pi 的那一项不会再次发送。
6. 作为切换 Session Path 核对历史的用户，我希望原路径的队列不会被送到当前看到的另一条路径。
7. 作为只是点开新会话但没有输入的用户，我希望离开后不产生任何 Pi Session；只有首次发送时才创建真实会话，并在失败时保留我已经输入的正文。

## Confirmed Constraints（已确认约束）

- Pi Session 继续是会话与消息的唯一权威；Swift 不直接读写队列目标 JSONL，所有消息写入经 Host 与 Pi SDK 完成。
- D Code 本机 Store 只拥有未完成所有权转移的 Queue Item 与必要派发收据，不复制已持久化会话历史，也不把队列正文写入诊断、Change Ledger 或搜索索引。
- 队列只属于当前稳定 Session ID 与确切 Session Path，不跨 Session、Project 或路径自动迁移；Session Copy 不继承源队列，Archive 不删除队列。
- 仍有待派发、正在派发或结果未知项目的 Session 不能移入废纸篓；界面引导用户先完成核对或撤回，不静默删除或遗留队列正文。
- `0.0.5` 只支持普通文本。以 `/` 触发的命令、Path Action、图片、附件、Skill / Prompt / Command 资源、Extension UI 回答与 Steer 均不入队。
- 写入门禁、租约、冲突检测、外部漂移、草稿恢复、日志脱敏和既有 Protocol 安全约束不得因队列而降低。
- Queue Item ID、Session ID、Path 锚点、Prompt ID、Entry ID、项目数量与正文大小均须校验并有界；损坏或未知版本不得被静默重写。

## Acceptance Criteria（验收标准）

### 新会话延迟创建

- [ ] 点击全局与 Project 内“新建会话”后，中央显示本地新会话 Composer，但 Host 没有收到 `session.create` / `session.open`，Pi 会话目录、Recent、Project 与 Search 均无新增对象。
- [ ] 空白或只有空白字符的会话前草稿在取消、切换 Project / Session、进入 Settings 或退出 App 后消失；再次新建不会恢复空对象，也无需执行废纸篓清理。
- [ ] 输入非空正文后切换页面与重启 App，再次新建会逐字恢复同一工作目录与正文，但仍没有 Pi Session ID 或 JSONL。
- [ ] 首次发送后只创建一个真实 Pi Session，并把同一正文发送一次；创建提交后即使旧列表请求晚到也不会隐藏 Recent 条目。
- [ ] `session.create` 失败时仍停留在会话前草稿且正文逐字保留；创建成功但 writable 打开或 Prompt 失败时，真实 Session 留在 Recent，正文转为该 Session 草稿并明确提示“会话已创建，但首次消息尚未发送”。
- [ ] 会话前草稿不启用模型 / 思考强度 / 极速、Context、命令、路径、附件或 Follow-up Queue，也不恢复冗余“对话”标签与信息检查器。

### 入队与管理

- [ ] 在一个真实运行中的 Session Run 内连续加入三条普通文本后，当前 Run 未被取消或 steer；三项只出现在 Composer 附近的待派发列表，顺序和正文逐字正确，Pi transcript / JSONL / Search 均没有提前出现它们。
- [ ] 编辑第二项、把第三项移到第一位并撤回原第一项后，界面与重启恢复的顺序一致；当前 Run、Session / Path、草稿和 Pi JSONL 不变。
- [ ] 本机 Queue Item 原子保存失败或达到已声明上限时，新增 / 扩容被拒绝，原 Composer Draft 与全部既有队列项逐字保留。
- [ ] 待派发列表、编辑、重排与撤回均可由键盘和 VoiceOver 完成，焦点不会因流式消息更新而跳失；状态在浅色、深色和 Increase Contrast 下不只靠颜色区分。

### 派发与幂等

- [ ] 前一 Run 正常收口后只派发当前队首；取得匹配 Session ID、Prompt ID 与持久化 Entry ID 前，它不从本机待派发记录消失，也不被显示为 Pi 消息。
- [ ] 第一项确认持久化并完成新的正常 Run 后才派发第二项；三项全程保持用户最后确认的顺序，同一 Queue Item 最多形成一个 Pi 用户条目。
- [ ] 当前 Run 的助手、工具与计划条目沿原路径正常追加时，Path Lineage Anchor 随已确认后继推进且队列继续；选择兄弟路径、从旧条目另起路径或出现来源不明的叶节点后，队列停住而不重绑。
- [ ] 单独的 `agent_end`、失败、中止、权限等待、用户输入等待、连接中断或外部冲突都不会触发下一项；剩余队列、顺序和正文跨刷新与重启保持。
- [ ] 在 Pi 用户条目可能已经落盘但 App 未收到确认的窗口强制终止并重启后，该项被恢复为已确认或“派发结果未知”，不会自动再发；后续项目在结果核对前保持暂停。
- [ ] 派发前切换 Session 或 Session Path、复制 Session、归档或检测到路径锚点漂移时，原队列不会进入新身份；返回后需要按停住原因完成显式继续或核对。

### 恢复、安全与回归

- [ ] App / Host 在纯待派发、正在派发、已持久化但 Run 未结束三个阶段分别重启时，恢复状态与实际 Pi 记录一致；没有丢项、正文截断、顺序漂移或重复用户条目。
- [ ] Queue Store 损坏、版本未知或不可写时原始字节保留，队列写入与自动派发被锁止并出现可执行错误；普通会话观察、历史阅读和文件预览仍可用。
- [ ] `/` 命令、Path Action、图片、附件、资源引用、Extension UI 回答和 Steer 不会被误收进普通文本队列，也不会以不支持能力伪装成功。
- [ ] 存在待派发、正在派发或结果未知项目时，普通直接发送不能越过队首，Session 也不能移入废纸篓；Archive 保留原队列，Session Copy 的新身份没有继承源队列。
- [ ] `v0.0.4` 的唯一无标签会话主页面、按需文件标签、Composer Draft、Session Path、搜索、复制 / 归档、共享观察、写入租约、信息检查器与文件安全回归继续通过。
- [ ] Host 和 Swift 自动测试、App 构建及真实运行候选分别记录命令、revision、工作区状态与覆盖范围；自动检查不冒充 VoiceOver、重启时序和运行中队列的人工验收。

## Out of Scope（非目标）

- Steer、修改当前 Run 的指令、自动中止或抢占当前工具执行。
- `0.0.6` 的 Activity View、完成关注态、完整 Run State、Interaction Dock、等待输入回复、停止、重试与统一状态转换界面。
- Goal / Work Map、D Team、多 Agent、后台多会话执行、跨 Session 消息与定时调度。
- Queue Item 级模型、思考强度、极速、权限或资源配置；斜杠命令、Skill / Prompt / Command、图片、附件和 Path Action 排队。
- Git stage / discard / commit / push、结构化验证证据、自构建、App 替换与发布；这些继续按后续版本和明确授权进入。
- 修改 Pi Runtime 的公开队列 API，或把 Pi TUI 的队列界面搬进原生 App。
