## 问题与目标

用户在一个任务的主对话中不断补充想法。若主智能体被具体执行占住，用户就无法持续讨论；若只得到一次子任务返回，又需要用户反复转述要求、协调多名成员和推动返工。

D Code 应让用户始终拥有当前任务的协调入口：简单工作直接完成，需要后台推进或分工时自主组织成员。用户可以与主智能体或任一子智能体对话，其他成员继续工作；成果经独立验收和协调者复核后交给用户。

## 本版范围与用户路径

| 用户要完成的事 | 本版行为 |
|---|---|
| 直接新建任务并持续讨论 | 协调者从首次对话承接，简单工作直办，后台工作主动派发 |
| 自动派发使用当前还能调用的模型 | 先确定该成员的模型回退链，再核验启用、访问、能力与配额；剩余 1% 及以下或无法确认的候选不自动选中，沿链选择下一个合格模型 |
| 从灵感材料开始一个任务 | 复用前一版已经成立的灵感引用，协调者按被选中的内容版本工作，再向成员提供必要的有来源上下文 |
| 在成员工作期间补充要求 | 主对话继续处理输入；可以定向提及成员，也可以进入成员子对话，相关变化回流协调者 |
| 收到可信成果并继续修改 | 执行、独立验收、协调复核与局部返工串联，所有结果和证据归原任务 |
| 停止、回收后继续某个成员 | 单独控制其主执行进程，保留上下文、来源和结果，后续以新进程续接 |

灵感是输入来源之一，多智能体协作属于 Task，不能只在灵感页面可用。当前任务引用的灵感内容版本不随画布后续编辑静默变化；成员仅接收该任务选定的有界投影，创建团队不自动加载全部灵感或知识库。

界面沿用前一版已经验收的导航区、工作区和信息区布局。本版增加真实成员、定向消息、回复来源、状态及相关操作，不进行整套视觉换版，也不以未接通的按钮、模拟成员或工具名称完成验收。

## 产品对象与职责

- Task 是用户可见的工作单位，可承载多段持续对话，主行进入该任务的 Coordination Session。单条用户消息或智能体回复是消息项，连续消息形成对话；Task 不等于某一条消息或其中任何一段对话。主会话和子会话使用不同稳定身份，不让每项子工作自动成为顶层 Task。
- 交互 Task 从首次提交起由该任务的 Coordinator Agent 承接；创建空草稿不要求启动模型或常驻进程。不同任务拥有各自的协调关系，不引入跨任务全局协调者。
- 一个 Task 可以包含多个 Work Item 和多个 Agent Run。执行、研究、验收等职责按工作需要配置；不固定一名执行者、一名验收者，也不为展示团队而启动无独立产出的成员。
- Coordinator 是角色，LLM 是其本次使用的模型。简单工作可以直接完成，转为专注协调时不更换任务或主对话；成员承担具体执行，协调者负责目标、派发、变更、冲突、复核与交付。
- 用户可直接进入成员的 Child Agent Session。选择成员、发送消息、返回主对话均不停止无关成员，不把正在观察的成员变成新的任务协调者。
- 运行成员只能由该任务协调者创建，用户可在主对话中要求它召集成员，不直接在界面新建运行成员；非协调成员也不能自行创建成员。用户编辑 Agent Profile 仍只是管理配置，不自动产生实例。主协调者由交互任务建立流程产生；已创建成员空闲回收后的进程重启不新建成员身份。

## 自适应派发规则

以下任一条件成立时，协调者应评估并在既有授权范围内主动派发，不等待用户反复要求组队：

1. 工作需要在后台持续推进，会妨碍主对话继续接收和处理用户表达；即使只有一项工作也适用。
2. 工作可以拆为具有独立完成信号的部分，分工能带来实际收益。
3. 工作需要不同专业判断或独立验收，不能只依赖执行者自述完成。

可在当前上下文中可靠完成、无需后台持续推进的小工作由协调者直接处理。不设“超过几步或几分钟就组队”的固定阈值，不把“存在多个 Agent 工具”作为组队理由。

派发前以简短可见说明交代分工与预期结果，随后实际启动成员；说明本身不是启动证据。任务范围内组队不增设每次用户确认步骤；改变目标、成本承诺、外部副作用授权或已有边界时，继续遵守相应用户决定与项目规则。

协调者需要实际具备本版允许的小工作执行、成员创建、派发、发送定向输入、停止受影响工作、安排验收与返工等能力；这些能力必须从真实注册工具和同一产品合同暴露。不能继续仅有只读协调角色，却用提示词宣称它可以直接完成简单写入工作或自主创建团队。成员创建边界由产品调用入口校验，不能只依赖模型遵守提示词。

每份 Agent Assignment 保留目标、范围、输入来源、完成标准、停止边界、回报对象和执行目录。提交原文与整理后的任务说明分开保存。多个成员可使用同一 Profile，但须分别建立执行身份、上下文、分工与进程绑定，不能共享一个在途执行实例。

并发数量受可用资源和既有设置约束。达到上限时工作明确等待，并保持协调对话可响应；不能为启动更多成员静默突破资源约束。多名写入成员继续使用独立且已验证的工作树。

## 模型候选与配额感知派发

### 可用性筛选

自动创建成员、开始新的模型调用阶段或在安全边界续接执行前，按顺序核验：

1. 先确定该子智能体自己的有序模型回退链，包括首选与后续候选；不同成员可有不同链。链来自用户或 Profile 已允许的配置以及本次明确选择，候选引用 D Code Model Catalog；不强制所有角色共用一条链，不按模型名字猜测能力，不静默加入链外模型。
2. 先排除用户未启用的模型；对应 Provider 具有当前有效的访问条件，Runtime 能实际选择该模型，并满足本次任务需要的工具、输入类型和上下文要求。仅有目录条目或已配置凭据引用不等于此时可调用。
3. 从该连接实际使用的账户、套餐或额度池查询当前配额。只查询已经通过前两步的候选所涉及的来源，复用并合并相同额度池的请求，避免每个子进程分别查询同一份额度。
4. 沿链选择第一个已启用、访问与能力成立，且所有适用约束窗口的有效剩余额度均高于 1% 的模型；1% 及以下不再自动派发给它，直接检查下一个候选。保存链的生效版本、实际选择、跳过原因和配额快照来源，不按剩余百分比重新排序回退链。

1% 是 507 确认的自动选用下限，不能擅自增加更高的预留阈值。比较使用有效原始百分比，不使用界面四舍五入后的展示值；例如 1.01% 符合配额条件，1% 与 0.99% 均跳过。仅有绝对余额时，只有服务端明确给出同一适用额度池的总量才能计算比例，无法确定则为未知。高于下限仍不保证整项工作一定够用，启用、访问、任务能力、并发和其他已确认边界继续适用。

初版覆盖本地既有 `openai-codex`、`zai-coding-cn`、`minimax-cn` 查询路径所对应的账户连接。模型具体名称和版本从真实目录发现，不把用户举例的模型版本写成固定白名单；其他来源必须经过相同适配与验证才能声明支持。

### 配额状态与范围

| 状态 | 自动派发行为 |
|---|---|
| 有效快照确认所有适用额度窗口剩余均高于 1% | 可以沿该成员既定回退链被选择；不保证额度足以完成整项工作 |
| 任一适用额度池或模型专属限额剩余 1% 及以下 | 跳过该候选及受同一低额度池影响的其他候选，不在同池模型间无效轮换；低额度与实际耗尽分别显示 |
| 暂时限流或容量不足 | 与套餐耗尽分开记录，尊重可验证的恢复时间或等待策略，不能永久标为无额度 |
| 缺字段、过期、查询失败、未支持或适用额度池无法确定 | 明确标为未知，刷新或换用有有效状态的候选；默认不进入自动派发，不把未知显示为零余额或满额度 |

配额快照至少保留来源连接的安全身份、适用账户或额度池、适用模型/功能、时间窗口、服务端可提供的剩余量或剩余百分比、重置时间、抓取时间与错误状态。身份不含可反推出凭据的正文。Provider 只返回百分比时就显示百分比，不能推算并承诺“还能完成多少任务”。

不同窗口、不同功能额度分别建模。某项工作实际需要的任一约束窗口剩余 1% 及以下就不能自动派发；无关功能低额度不应误伤普通文本调用。不能把所有 Provider 都强制转换成“5小时加每周”，也不能把同一订阅池误拆成每个模型各有一份额度。

快照过期或发生额度错误时先失效，再刷新；重置时间到了也需重新取得可用证据，不能仅凭本机时钟把额度改成满额。单个来源失败不阻断其他来源的有效结果。并发成员共享同一额度视图；额度请求合并、过期处理与运行反馈一起防止不断使用已耗尽的池。

### 回退与运行中的额度变化

配额在查询与调用之间仍可能变化。新快照到达 1% 或以下，或收到可确认的额度耗尽错误后，更新相应模型或池的状态，停止向该池继续派发，并沿受影响成员各自的既定回退链选择其他合格来源。普通网络错误不能被当成耗尽，也不能触发无依据的永久禁用。

运行中的模型切换只发生在受控续接边界，保存真实模型与新调用事实，不热迁移在途生成、工具执行或阻塞交互。已经完成的动作不因回退自动重放；存在未知外部副作用时先核对并安全收口，再继续。

回退改变该成员后续使用的模型，不新建顶层 Task，不把它伪装成另一个用户可见成员，也不复制一个同时活动的主执行进程。任务职责、上下文与报告关系保持可追溯；如果 Runtime 需要重开，先安全结束旧进程，再建立新绑定并续接。

链内所有候选均处于 1% 及以下、不可访问或无法确认时，工作进入明确等待/阻塞，显示原因及有依据的重置时间或恢复入口；不得声称成员已启动。该状态也可能影响协调者自身的模型响应，客户端需如实呈现，不能以“保持对话可用”伪造模型回答。不得静默升级套餐、购买额度、更换到未授权的按量计费账户，或为探测可用性发送未经授权的推理请求。

### 现有能力复用

优先使用 507 已有实现作为来源，不重新从零设计查询路径：

- [`pi-dusage`](https://github.com/ssdiwu/pi-dusage)：复用各 Provider 的只读查询、额度窗口归一化、版本化快照、抓取时间、安全错误、并发刷新合并和失败隔离逻辑。现有快照用于展示，接入自动路由前须补齐适用额度池、有效性及缺字段语义，不能把显示默认值当成可调用证据。
- [`pi-dteam`](https://github.com/ssdiwu/pi-dteam)：复用显式模型候选链、候选去重与回退次序的成立机制，接入前增加配额资格筛选；现有“能解析模型”不能等同“有额度”。不强制迁入其固定档位或旧团队所有权。
- [`pi-dstatus`](https://github.com/ssdiwu/pi-dstatus)：只作为结构化额度消费者的展示参考，不能从 Footer 文本反解析调度事实。
- [`pi-key-pool`](https://github.com/ssdiwu/pi-key-pool)：参考限流、容量、配额和网络错误的分类及停止重试机制，不在本版新增密钥池、改写 Pi 凭据或自动复制其固定冷却时间。

D Code 复用查询和归一化核心，凭据仍通过已有安全引用或 Runtime Auth Bridge 使用；不直接把依赖 `pi-tui` 的整个扩展入口装进产品，也不新增持续读取/同步 Pi 配置的产品权威。接口、字段与授权路径在实施时以当前来源和最小授权只读查询复验，不能仅凭旧 README 认定接口仍有效。

## 主对话、子对话与途中变更

主对话支持用户 `@` 同任务中已创建且可接收工作的成员。提及选择的是有稳定身份的现有成员，不按名字隐式创建；目标不存在、属于其他任务或已不可接续时给出明确反馈，用户可以改向协调者提出需求。此动作不提供绕过协调者的新建或克隆入口。

消息原文保存在发出它的对话中，单独记录实际发送者、目标成员和相关工作引用。目标成员收到定向输入，协调者同时收到有来源的指令与变更事件；无需用户再转述。成员对这条消息的回复回到原对话并显示真实成员来源，不伪装成协调者发言。消息出现在哪个对话不决定成员的进程身份，不因主对话和子对话分别收到消息就为同一成员同时启动两个主执行进程。

后台成员执行期间，协调者可以接收用户新消息、回答进度问题并调整任务，不等待整批成员结束才再次处理用户表达。客户端切换和模型运行是两件事；此承诺不包含 App 退出后继续运行。

主对话的补充材料或新要求应定向传给相关成员，在可接受输入的安全边界生效；不会原位覆盖已经保存的生效输入和执行证据。若旧方向不应继续，协调者停止或撤销受影响的后续工作，并明确哪些动作已经发生。

用户对子智能体直接补充或修改要求后，影响任务范围、进度、结论或其他成员依赖的变化应形成有来源的协作事件并通知协调者。保留原始消息，不伪造成主智能体或用户在其他会话重新发言。协调者不得因为同步较晚而用旧指令默默覆盖用户更新；涉及相互冲突或超出任务边界的意图时，只请求必要的澄清。

事件包含稳定身份、目标、相关工作与来源引用，避免重复送达造成重复执行。主对话无须复制成员完整聊天或私有过程；用户可以从状态、报告和来源回到对应子对话。主对话中的明显独立新目标应明确其归属，不静默扩展当前任务。

## 独立验收、复核与返工

- 需要独立验收的工作由不同于原执行者的 Agent Run 承担，可按成果类型组织多名验收成员。验收以任务标准、实际成果和可核验证据为依据，执行者自述不作为通过事实。
- 成员提交报告后，协调者复核任务覆盖、证据充分性、相互矛盾与用户最新要求，不能只读取“通过”标签即宣告完成。
- 成果有问题时回到相关执行成员返工，之后再次验收；验收遗漏或依据不足时，要求验收成员重新检查。不同工作项可独立循环，不无故重跑已经通过且未受影响的部分。
- 一般性返工在任务授权内继续推进，不要求用户反复回复“继续”。同类尝试连续两次没有新证据、也未缩小问题时，协调者必须调整方法或重新分工；确需改变目标、成本或风险时，再把具体决定交给用户。
- 验收通过、协调者复核、用户接受、测试通过、提交和发布分别成立。协调者向用户交付成果、必要证据与待决事项；正式 Task 接受沿用现有结构化验收请求，不能由成员或协调者文案代替。

## 智能体与进程约束

本规格使用根术语表中的 [Agent Execution Process（智能体执行进程）](../../GLOSSARY.md) 表达主执行锚点在运行期间的一对一关系，覆盖主智能体与所有成员：

- 一个正在运行的 Agent Run 恰有一个独立的操作系统主执行进程；该进程只承载这一个 Agent Run，同一智能体可以有多个可归属的工具辅助进程。
- 不允许多个智能体只以同一进程里的 Runtime 实例实现，也不允许同一 Agent Run 同时拥有多个智能体执行进程。
- 并行调度必须为主对话保留继续处理输入的能力，不能让所有可用运行名额都被成员占满后使协调者只能等待。具体资源管理方式由实施确定，并以真实并发输入路径证明。
- Profile、会话和历史 Run 可以没有活动进程；重启是旧进程退出后的新尝试与新绑定，不是创建第二个同时活动的执行者。
- Host、窗口、浏览器或命令工具的辅助进程不等于智能体实例，必须保持来源归属和生命周期可解释。
- 单独停止或异常终止成员不应中断协调者与无关成员。Host 仍拥有产品事实写入与外部副作用边界，进程隔离不产生新的 Product Store 所有者或权限模式。

## 空闲驻留、回收与上下文续接

主执行进程在本轮工作收口后可以短暂空闲驻留，以便继续交流；系统随后可以安全回收，无须让所有已完成成员长期占用进程。驻留时长不在本规格固定，不能因超时机械丢弃尚未保存的上下文或在途工作。

回收前必须确认上下文、报告和成果引用已经持久化，在途工具、阻塞交互和外部副作用已经收口或进入可解释的安全状态，并处理辅助进程。再次收到该智能体需要处理的工作时，使用持久化上下文及有来源的相关记忆启动新主执行进程，保存新进程绑定；旧会话和智能体身份保持可追溯，不自动重放完成操作。上下文丢失或无法恢复时明确报错，不只靠摘要伪装完整续接。

## 验收标准

- [ ] 创建交互任务后，主对话由该任务的协调者承接；简单工作无需组队即可完成，同一任务中的后续复杂工作不要求更换主对话。
- [ ] 不同成员可持有不同有序模型回退链；自动选择严格沿各自链的顺序，不按全局单一链或剩余百分比重排。
- [ ] 已启用且有访问条件、但当前适用剩余额度为 1% 或更低的模型被自动跳过；后续首个合格候选被实际使用，1.01% / 1% / 0.99% 的边界及界面取整差异均有验证。
- [ ] 共享额度池降至 1% 或以下时，同池的不同模型全部正确退出相关自动候选；无关功能限额不误伤不使用该功能的任务。
- [ ] 缺字段、查询失败、过期和未支持来源显示为未知且不冒充可用；一个来源失败不影响其他来源。不存在有效候选时真实等待，不伪启动成员。
- [ ] 同一批多成员派发复用同池查询；额度在运行中耗尽时，错误回流并阻止后续派发，安全回退不重放已完成副作用、不热换在途运行，也不进入未授权付费来源。
- [ ] 重置或补充额度后经重新查询确认高于 1% 才恢复候选资格；账户连接、模型专属额度与各时间窗口映射经脱敏响应和最小授权只读查询验证，凭据不进入界面、普通日志或模型上下文。
- [ ] 交付一项需要后台持续推进的工作后，成员仍在执行时，用户能在主对话完成一次新消息交互；不能仅显示“运行中”就视为对话仍可用。
- [ ] 同一任务可按需运行至少两名执行成员和两名独立验收成员，职责与工作项可追踪；这个验收样例不成为固定人数配置。
- [ ] 用户能在任一成员子对话补充材料或要求，再返回主对话；原文、目标成员和任务变化可回查，无关成员继续运行，协调者能获知相关变更。
- [ ] 主对话中提及一个已创建成员并交办新要求，目标成员收到、协调者获知，成员回复回到主对话并标明来源；用户无需切页或重复转述，同一成员不会因来自不同对话的消息产生两个活动主执行进程。
- [ ] 没有成员时用户只能要求协调者创建，不能从新建成员按钮、提及未知名字、复制入口或非协调成员的调用绕过创建边界；用户编辑档案不产生运行成员。已有成员进程回收后的上下文续接不误建第二个成员身份。
- [ ] 延迟或重复送达的变更不会重复启动工作，也不会用旧要求覆盖已采纳的新要求；范围冲突明确暴露。
- [ ] 成果不合格触发执行返工，验收不充分触发重查；问题消除后重新验收并由协调者复核，不需要用户逐轮催促。
- [ ] 连续无进展的返工不会无限重放同一操作；方法调整、重新分工或需用户决定的边界有真实记录。
- [ ] 运行证据能把每个活动 Agent Run 对应到唯一、不同的操作系统执行进程，并证明进程只服务该实例；逻辑 Runtime 标识不能代替此证据。
- [ ] 单独结束一名成员执行进程后，其状态明确失败或停止，协调者和其他成员仍可工作；恢复前确认旧进程已终止，不制造同时活动的重复实例。
- [ ] 成员报告、验收报告、协调复核、用户接受与发布分别可辨认；产物及证据仍归原任务。
- [ ] 成员完成后经历空闲回收，再次进入该成员子对话发送补充要求，系统使用新进程正确续接已持久化上下文；原报告与消息保留，已完成动作不重复执行，辅助进程去留可解释。
- [ ] 资源不足时显示真实等待而非伪启动；停止与恢复不遗留无法归属的工具辅助进程或未知外部副作用。

## 实施依赖与切片规划

三个阶段都属于 `0.0.31`；本节定义逐步证明的能力与进入下一阶段的条件，不指定易变的内部文件或 API 名称，不以文档落盘自动授权实现。

1. **独立执行与模型供给基础**：先证明主智能体和成员的独立主执行进程锚点、辅助进程归属、事件归属、单独停止、空闲回收、上下文重新启动与故障隔离；同时复用已有模型与额度能力，证明候选资格、额度池映射和失效回退。Product Store 单写入不变，未通过前不替换在役 Runtime 路径。
2. **持续沟通与自主派发**：接入简单工作直办、协调者独占的成员创建、后台派发、主对话提及已有成员、直接子对话和变更回流；用成员执行期间真实完成新一轮主对话的动作验收。
3. **独立验收与返工闭环**：按工作项连接执行、验收、协调复核、局部返工与用户接受，验证多成员并行及停止条件，不以一次团队成功替代完整闭环。

| 阶段 | 必须证明的完整动作 | 不得作为替代证据 |
|---|---|---|
| 独立执行与模型供给基础 | 额度耗尽候选被跳过，有效候选实际启动多个独立主执行进程；单独停止、空闲回收、基于原上下文重开 | 仅目录中有模型、额度字段缺失按满额处理，或不同进程数量却没有稳定成员对应关系 |
| 持续沟通与自主派发 | 后台成员仍在执行时，主对话真实完成一轮新交互；提及成员并收到有来源回复；进入子对话改要求后协调者获知 | 输入框看起来可用，但消息只能等团队全部结束才处理 |
| 独立验收与返工闭环 | 多项工作分别执行与验收，一项故意不合格后局部返工、复验并回主对话；无关成果不重复重做 | 并行启动一次成功、执行者自称检查通过或汇总一段“全部完成”文字 |

每个切片单独记录实现和验收，通过后再推进下一切片；若新发现需要改变本版目标或已确认边界，回到该项决定，不把失败能力暗中移出验收清单。版本索引记录实施与发布状态。

## 完整版本验收与回归边界

完成本版前，至少在真实客户端中跑通一条组合路径：从一个已选定版本的灵感创建任务，协调者按需组织多名执行与验收成员；用户在执行中继续主对话、提及成员并进入一次子对话修改要求；一项成果验收失败后局部返工，协调者综合结果并发起用户验收；成员空闲回收后再续接。另以直接新建任务验证同一协作能力，不要求经过灵感入口。

组合路径应包含一项剩余额度为 1% 或以下的候选被跳过、沿同一成员回退链选择另一有效候选并实际使用的证据。耗尽、未知、共享池和途中限流可使用受控脱敏响应制造边界，实际有效候选的模型调用与任务结果仍须单独核验，不消耗真实账户额度来刻意制造耗尽。

自动回归使用隔离数据与可控运行反馈，覆盖进程身份、事件归属、原文与生效输入、定向消息去重、过期输入、失败传播和恢复。组合路径仍需有真实模型与工具活动的候选走查，不能只替换模型返回后宣布自主协作已经成立。真实账户和外部副作用使用明确授权的验证范围。

前一版的任务创建、草稿、切换、附件、灵感内容版本及引用、重启恢复和核心输入交互均须回归。任何数据升级先建立隔离恢复与回退方案，不假定旧客户端能够读取升级后的数据，也不以回滚 App 掩盖数据不兼容。

本版完成信号是：本规格所有验收项和上述组合路径成立，当前必要检查通过，507 完成人工验收，并留有候选及恢复证据。提交、推送、签名、发布分别授权和核验，不由 PRD 完成或自动检查推导。

## 非目标

跨任务全局协调者、固定三人团队、全量共享聊天上下文、自由无限互聊、云电脑、移动接入、App 退出后常驻服务，以及新增权限模式均不在本规格内。复制某名成员的在途上下文、分叉或合并执行血缘尚未形成独立功能合同；本规格中的多成员是分别创建实例，不把用户提到“复制”推导为完整克隆能力。
