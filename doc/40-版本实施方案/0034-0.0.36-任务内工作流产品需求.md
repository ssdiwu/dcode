状态：507 于 2026-09-28 选择“真实工作流：可创建、运行和继续任务内工作流”，最初计划在 `0.0.35` 实施；随后认可先收口现有功能与安全的版本拆分，本文件调整为 `0.0.36` 的工作流行为与验收。输入区入口、菜单层级和视觉交互由同版 [PRD 0033](0033-0.0.36-协作过程可视化与工作台质感产品需求.md) 承接。2026-09-29 至 30 主树未提交地接入 Product Store 工作流身份、阶段、运行、证据与恢复合同，以及“＋”表单和阶段面板；Host／客户端组合自动回归与隔离 Electron 定向路径通过，真实模型的完整成员交付、性能对照与 507 人工验收仍未收口。`0.0.35` 的[稳定性与安全修复](0035-0.0.35-现有功能与安全加固产品需求.md)是本版代码与验证的先行基线；`0.0.34` 人工验收仍独立记录。

## 问题与目标

用户想从任务输入区发起一项有多个步骤、成员或检查门槛的工作，并在执行中看清进度、补充要求、停止和继续。D Code 目前已有 Task Goal、Plan、Work List、Team Run 和 Agent Run，但它们尚未形成一个可由用户明确选择、创建、运行和接续的“工作流”入口。把“计划”改名或仅插入一段提示词，会让用户误以为有可恢复的执行能力。

本版让工作流成为 **Task 内可追踪的执行安排**：保存目标、阶段与依赖，使用当前任务的工作项和成员执行能力推进，记录每阶段的实际状态、产物与证据。用户从输入区选择“工作流”后，可以在同一 Task 中发起、查看和安全续接；主对话始终可继续讨论。工作流结束仍不替用户接受 Task。

## 用户路径与行为

1. **发起**：用户在新任务草稿或已有 Task 的“＋”面板选择“工作流”，输入要完成的结果、范围和必要限制后显式提交。新任务首次提交仍只创建一个 Task 和协调会话；已有任务不被复制成新 Task。提交原文与协调者整理后的工作流安排分别保存，菜单选择本身不创建运行实例或发送消息。
2. **形成可查看的安排**：协调者按已提交目标形成有界阶段，说明每阶段做什么、前置条件、完成信号、产物或检查要求、停止边界及预期成员分工。工作流有稳定身份和版本；用户可在运行前查看和修订安排。既有 Task Goal、Plan 和 Work List 继续各负其责：工作流负责一次可执行安排及其阶段进展，不复制第二套任务、计划或工作清单权威。
3. **开始与推进**：在现有任务授权内，协调者可以在简短可见说明后启动工作流，不为每次成员派发增加确认；改变目标、成本承诺或外部副作用边界时仍请求必要决定。阶段按真实依赖串行或并行推进，具体工作由 D Code 当前 Task 的 Work Item、Team Run、Agent Run 和 Child Agent Session 承接。只有明确归属该工作流阶段的工作项、交办和成员才进入它的进度与结果；创建工作流不能事后接管一个已经在途的普通 Team Run。同一 Task 可保存多轮工作流记录，但不同时启动两个相互独立的工作流来争用同一任务的运行与写入所有权；若已有不属于该工作流的 Team Run 正在执行，新工作流明确等待或拒绝启动并说明原因，并行只发生在一轮工作流内部。
4. **观察和介入**：主对话中的工作流卡与 Task HUD 显示当前阶段、待处理输入、阻塞原因、成员、已形成的结果和下一步；具体成员过程、产物、Diff、报告和证据按需进入已有子对话或信息检查器。用户可在主对话补充要求或进入成员子对话，影响阶段或其他成员的变更回流协调者。界面不从模型自述推导“阶段完成”，也不把工作流完成显示为 Task 已验收。
5. **停止、失败与续接**：用户可停止工作流的后续推进，已完成的文件或外部操作及其记录保留。失败、额度不足、容量等待、目录冲突、Host 退出和结果未知分别给出状态与可行的下一步。重开应用或选择“继续工作流”时，D Code 从已保存的工作流身份、阶段、交办与证据接续；消失的模型生成或工具执行不伪装热恢复，已完成或结果未知的外部副作用不得自动重放。
6. **修订与收口**：运行中修订安排只在安全边界作用于后续阶段，旧版本、原始交办与已发生结果继续可查。工作流完成需有阶段结果和要求的验证证据，形成有来源的整体报告；仍由协调者核对 Task Goal 和最新用户要求，必要时继续返工、独立验收或提出用户验收请求。用户可以回看历史工作流，但历史状态不冒充当前活动。

## 已确认约束

- 工作流属于一个 Task，不是 Project 与 Task 之间的新层级、跨任务全局调度器或新的 Agent Runtime。具体持久化形状与调度接缝由实施阶段在 D Code Product Store 和现有运行合同中确定，不让 Pi 会话、外部插件或 UI 内存成为权威。
- Task Goal 说明要达到的结果；Plan 说明当前采用的路线；Work List 保存可跟踪工作项；Team Run 和 Agent Run 保存真实成员执行；Workflow 把一次有界执行的阶段、依赖和续接关系组织起来。阶段可绑定启动前已存在且未执行的工作项；普通团队已完成的结果可明确引用为输入，但不追认为本轮工作流执行的阶段，不为展示复制同一成果或事实。
- 模型可用性、配额门槛、并发上限、目录单写入、独立成员进程、用户消息原文、来源回执、外部副作用 unknown（结果未知）和任务验收继续遵守既有合同。工作流不能绕开这些边界。
- 阶段完成从所绑定 Work Item、Agent Run、报告、独立检查、协调复核及必要 Evidence 推导，不建立一套由脚本或界面单独置绿的完成状态。无关联的普通团队工作仍归原 Task，可作为后续明确引用的历史输入，但不自动成为该工作流已经执行的阶段。
- ZCode 的“工作流”是一个真实动态编排机制；其“＋”菜单只在对应命令可用时提供入口，点击后先写入命令而非直接运行。D Code 借鉴可发现入口与运行过程分层，按自身 Task 语义实现用户已确认的创建、运行、继续能力；外部脚本格式和执行器不自动成为本版需求。来源见[参考索引](../参考文件/README.md)。

## 验收标准

- [ ] 从新任务草稿选择“工作流”，提交两阶段目标后只建立一个 Task；工作流安排、用户提交原文与 Task Goal 分开可查。取消菜单、放弃未提交草稿或创建失败均不留下假工作流执行。
- [ ] 从已有 Task 再发起一轮工作流，实际建立可查看的阶段与依赖；一项独立工作由成员完成，后续阶段消费其真实结果并经过不同成员检查。主对话在后台推进期间继续接受用户输入；成员和阶段状态与任务内报告、证据及子对话一致。
- [ ] 前一阶段阻塞、失败或待用户回答时，依赖它的后续阶段不被标为已开始；无关且已完成的阶段不因局部返工重跑。容量、额度、目录与模型失败沿原有任务合同等待或回退，并说明原因。
- [ ] 工作流在真实文件修改后停止，再从同一稳定身份继续；已完成写入与检查不重复执行，旧交办与新要求分别保留。Host 重启后丢失的在途执行显示中断，未知副作用阻止自动重放，用户可以核对并决定后续动作。
- [ ] 同一 Task 的第二轮工作流与第一轮身份、阶段计数和产物分开；同时启动另一独立工作流被明确拒绝或排队，不共享一个在途成员进程或写入者。历史轮次可回看，最近完成轮不伪装运行中。
- [ ] 在同一 Task 已有未绑定的普通 Team Run 运行时发起工作流：普通成员继续在原团队中，工作流显示等待或拒绝启动的原因；普通团队结束后工作流再开始。两边的工作项、成员、报告和阶段计数不交叉，已经存在的普通结果只有经明确引用才能作为工作流输入，不冒充已执行阶段。
- [ ] 工作流报告、独立验收、协调复核和 507 对 Task 的接受分别成立；仅凭脚本退出、成员最后一句、所有阶段显示绿色或自动检查通过，不把 Task 改为已验收。
- [ ] 隔离自动回归、真实 Host／客户端与可控模型的完整路径、实际 Electron 界面和 507 人工验收分别记录。覆盖新任务／已有任务、并行与依赖、停止／恢复、失败／未知、浅深主题、窄窗口、键盘和减少动态效果；正式数据及外部副作用只在对应授权范围内验证。

## 非目标

- 不建立跨 Task 的可复用工作流市场、定时触发、云端调度或自动发布；本版的“创建”指当前 Task 内有持久身份的安排，后续跨任务模板另行定义。
- 不要求用户编写或运行任意 JavaScript／TypeScript 工作流脚本，不移植 ZCode 的脚本引擎或其 `CreateWorkflow` 工具作为 D Code 运行依赖；具体实现可以复用现有协调和成员机制，只要上述可观察行为成立。
- 不以工作流取代 Task Goal、Plan、Work List、Team Run 或验收，也不把一次工作流执行提升为顶层 Task。
