# D Code 0.0.33 协调者按需探索与路线选择产品需求

状态：507 于 2026-09-26 确认需求并授权分批提交后开始实施；当前为隔离分支实现候选，完整版本验收尚未完成。版本顺序为 `0.0.32` 工作台收口 → 本版协调者按需探索与路线选择 → [0.0.34 任务续接与可追溯审查](0031-0.0.34-任务续接与可追溯审查产品需求.md)。当前隔离分支 App/Host 构建号为 `0.0.33`，本规格不代替 [PRD 0030](0030-工作台-UI-UX-并行候选.md) 的候选和验收记录。

## 问题与单一用户结果

D Code 已有任务内自主派发、独立验收与局部返工的产品合同，但目标明确不代表做法已经可靠。如果协调者过早围绕第一条看似合理的路线拆分工作，多个成员可能在同一个错误前提上持续投入；等成果验收失败再返工，代价会沿依赖传播。反过来，让所有任务强制生成多个方案，也会拖慢原本可以直接完成的小工作。

本版交付一个完整结果：**同一 Task 中，协调者依据任务的不确定性决定直接推进、补查事实或探索路线；需要探索时，用可核对的候选、反证和验证结果选择足够成熟的路线，再组织执行，并能在路线失效时有依据地退回探索。** 用户能看懂当前在验证什么、为什么采用这条路线、还有什么没确定，并在原对话中继续指导工作。

## 用户路径与行为

### 1. 判断当前需要解决的问题

| 当前情况 | 协调者行为 |
|---|---|
| 目标、约束和可靠做法均已明确 | 直接推进；需要后台工作或独立分工时仍按 PRD 0029 派发，不增加探索专属轮次或成员。 |
| 缺少可查明的事实 | 先读取当前项目材料或进行有界核验，再判断是否存在真实路线分歧。 |
| 目标明确，但关键做法存在会影响结果的不同路线 | 进入有界探索，说明待检验的关键假设及预期结果。 |
| 取舍会改变用户目标、范围、成本承诺或风险边界 | 给出具体候选、依据和代价，请用户决定；其余独立且已授权工作可以继续。 |

判断发生在任务开始及关键新证据、用户变更或失败出现时；不在每轮对话重复完整分类，不按步骤数、耗时或“有多智能体工具”机械触发。事实缺口、路线分歧和用户取舍可以同时存在，但不把可自行查明的事实转成用户选择题。

### 2. 形成可检验的候选路线

- 每条候选说明目标与适用约束、核心做法、关键假设、已有依据、主要失败条件、最小验证动作和预期成本。引用保留实际来源及适用版本；猜测、待检验假设和已核实事实分开表达。
- 候选的差异应影响结果、依赖或代价，例如不同机制、实现路径或问题表述。不能把同一方案的改写凑成多个选择。候选数量按问题和可用资源确定，不固定为每项任务必须两条或三条。
- 协调者可直接开展小规模探索；需要独立方向、专业判断或后台工作时，在同一 Task 内派发成员。成员只获得所需的有界任务包与来源，不默认共享全部对话；原有成员创建、独立执行进程与单写入边界继续有效。
- 探索可使用已有工具查资料、检查代码或做低成本验证。验证动作必须处于现有任务授权和工作区隔离内，不因“只是试方案”扩大写入范围或外部副作用。

### 3. 检查关键假设并判断能否实施

- 对关键路线的检查以具体缺陷为目标：寻找反例、边界条件、缺失前提、依赖冲突及与原目标不符之处。需要独立判断时，由不同于候选提出者的 Agent Run 检查；独立身份不要求强制使用另一家模型，也不保证结论正确。
- 检查结论保留被检查的候选版本、具体问题、支持或反驳证据及未覆盖范围。能用资料、可执行测试或小实验核对的关键主张应实际核对；未检查、工具失败或未找到反例都不能表述为已经证明正确。
- 协调者可以选择、修正或组合候选；组合后的路线需要重新检查被改变的假设和依赖。原有反证、未解决异议与失败原因随相关内容保留，不能在汇总时消失；多数赞同或笼统高分不能抵消一个有证据的致命缺陷。
- 一条路线足以进入实施，须同时满足：核心做法已有支持且没有未处理的致命反例；剩余未知可以表述为明确、可分配和可验证的工作；各部分的依赖与完成标准清楚。允许存在困难的子问题，但不能把可能推翻整体路线的前提隐去后派发为普通执行。
- 协调者记录采用依据、剩余未知和适用的目标及约束版本。该判断只表示值得继续投入，不代表成果验收或用户接受。全部候选都不足时保留这一结果，在有新信息预期且预算允许时继续探索，否则明确当前阻塞、已获证据及最小下一步。

### 4. 执行、局部返工与重新探索

- 采用路线后，沿既有 Plan、Work List 与 Agent Assignment 组织工作，表达依赖、完成标准、报告对象和停止边界；仅有依赖已经满足的工作才进入相应执行，独立工作可以并行。后台成员工作期间主对话继续接收用户表达。
- 验证发现局部问题而核心路线仍成立时，沿受影响工作项返工；若关键前提被否定，则退回探索，标记旧路线的失效依据，停止受影响的后续工作，并重新核对依赖该前提的已完成成果。无关且仍有效的成果保留。
- 用户新要求或来源版本变化影响路线时，先核对其适用性；旧成员的迟到报告保留原来源，但不能覆盖较新的任务约束与路线决定。协调者说明哪些动作已经发生，未知外部副作用不自动重放。
- 成果按既有规则按需安排独立验收，再由协调者复核并提交用户验收；不因增加路线选择而要求所有小任务固定启动验收成员。路线检查、工具检查、成员报告、协调复核、用户接受、Git 提交及发布分别成立，沿用 [PRD 0029](0029-任务内自适应协作产品需求.md) 的既有合同。

### 5. 有限投入、保存与呈现

- 每轮探索开始前确定有界的目标、候选与验证投入以及停止条件，服从现有并发、模型回退链、配额与用户成本限制；不为探索静默增加付费来源。达到本轮限制后给出结果与剩余问题，不能以新建一轮的方式反复清空累计投入或失败记录。
- 同类尝试连续两次既无新证据也未缩小问题时，遵守既有停止规则，调整方法或分工；不能把换表述、换成员或重新打分当作进展。缺少可用资源、验证中断或用户停止时显示真实状态。
- 候选、反证、采用依据、验证结果和失效关系归原 Task，以既有 Plan、Finding、Agent Report、Artifact 与 Evidence 关系承载；保存可复核的工作产物，不要求记录隐藏推理或将完整成员上下文灌入主对话。具体数据形状由实施确定，不另建方案或任务权威。
- 本版须能从已有任务、成员与报告入口查看这些记录；重启或成员重新执行后，能读取已保存的当前路线及其适用版本，避免丢失决定、重走已证伪路线或伪装恢复在途执行。自动工作摘要、范围内历史召回和统一来源回跳由 `0.0.34` 完成，本版不依赖它们才能运行。
- 主对话突出当前待验证问题、采用路线的依据、未决项和改变方向的原因；详细候选与检查过程按需进入已有报告和成员会话。状态以真实记录为依据，用户能纠正前提或补充约束，无须逐次点击同意组队或内部路线选择。

## 已确认边界

- D Code Product Store 继续拥有 Task、Plan、Work Item、Agent Run、报告与证据；Pi SDK 只提供运行能力。成员创建、进程隔离、配额、工作区写入及用户指导回流继续由 [PRD 0029](0029-任务内自适应协作产品需求.md) 和 [ADR 0045](../决策档案/0045-任务内自适应协调与智能体进程边界.md) 拥有。
- 语义判断由协调者及所需检查成员结合证据作出，产品层保证身份、来源、版本、作用域和状态真实。模型的判断文字不自动成为结构化完成事实；Prompt 与活动工具继续同源，不描述未注册能力。
- 本版使用当前任务已经可访问的材料与已保存记录；不静默扩展 Task Context Selection，不以候选搜索扩大跨项目读取或持久上下文。提交原文、生效输入与后续摘要继续分离。
- 本版是任务执行方式的改进。三篇论文的来源与借鉴边界见[参考索引 REF-022–024](../参考文件/README.md#ref-022024-harness-论文)；论文结果不作为 D Code 已实现或验收的证据。

## 验收标准

以下勾选表示相应功能经本轮自动验证与507授权的代理桌面测试覆盖；整体收益门槛及507本人产品验收另行成立。

- [x] 一个目标和做法明确的小任务直接完成，无探索专属模型调用或成员；另一个仅缺事实的任务先核验事实，不无故请求用户选择。
- [x] 一个存在真实路线分歧的任务形成可区分的候选，每条具有关键假设、失败条件和验证动作；其中一条看似合理但有可复现缺陷，检查能定位具体问题并影响最终采用决定。
- [x] 没有候选足够成熟时，不伪造已采用路线或启动依赖其成立的正式实施；预算或资源不足时能查看已有结果、未决项与停止原因。需要用户取舍时，只询问会改变目标、成本或风险的决定。
- [x] 路线组合或修订后，受影响假设得到重新检查；历史反证和未决异议仍可查。只有同时满足成熟条件才进入实施，主对话能说明理由和剩余未知。
- [x] 同一 Task 走通“探索 → 检查假设 → 采用路线 → 按依赖分工 → 验证成果”。故意制造一次局部缺陷只返工受影响部分；另一次否定核心前提会退回探索，并核对受影响的下游成果，无关工作保留。
- [x] 探索或执行中用户修改约束，相关成员收到变化并停止过期方向；迟到报告不能覆盖新决定。用户继续主对话、定向提及成员及进入成员会话的既有能力不受影响。
- [x] 重启或成员进程回收后，原 Task 的路线、来源版本、验证与失效记录仍可查看和用于继续工作；已完成副作用不自动重放，失去的 Runtime 不显示为继续运行。
- [x] 达到探索投入限制、连续两次无进展、检查工具失败、模型不可用与用户停止均有真实结果；换一轮或换成员不清空累计投入，不以未知或未发现问题冒充验证通过。
- [x] 主对话的简洁状态与报告中的真实记录一致，用户能从既有入口检查和纠正前提；相关交互在键盘、深浅主题与窄窗口下可用。路线成熟、成果验收和用户接受有明确区分。

## 对照验证与交付信号

使用简单任务、事实缺口任务、多路线任务、核心路线失效任务及用户中途变更任务验证。候选与原流程采用相同任务快照、模型版本和相近总预算；预先固定完成标准，保留一组未参与调试的任务。记录最终正确性、无效返工、总耗时和模型用量，比较须包含探索、检查、执行及返工的全部投入；缺少费用数据时如实报告，不虚构货币成本。

上述场景验收须通过；在未参与调试的多路线或路线失效任务中，应有可复验的最终正确性改善或无效返工减少，且简单任务不新增探索开销。收益波动时重复足够的对照以判断是否成立，不以单次幸运结果或额外预算宣称改进。未观察到收益的候选继续调整或保留为未通过，不能替换在役流程。

文档确认、行为测试、对照任务、真实客户端完整路径、507 人工验收、提交与发布分别记录。实现按可验证能力推进，最终须在同一任务中完成探索、执行、失败回退、继续工作与用户验收的真实组合路径；不能只改提示词或使用固定模型返回就宣称自主路线选择已经交付。

## 非目标

- 不强制所有任务走多方案流程，不固定候选数、团队人数或模型品牌；不复制论文的大规模搜索树、投票机制或整套研究平台。
- 不在本版自动演化 D Code Harness、修改自身工作规则、训练或蒸馏模型；RRSI 的受控比较用于验证纪律，Harness-Zero 保留为训练方向参考。
- 不提前交付 `0.0.34` 的自动摘要、通用召回与统一引用回跳，不建立第二任务系统、通用工作流编辑器或无限探索引擎。
- 不新增提交、合并、推送、发布或用户任务验收权限；不绕过现有候选隔离、恢复与回滚边界。
