# D Code 0.0.27 自进化运行回执与安全恢复产品需求

状态：Published Source Tag（公开源码标签 `v0.0.27`；自动门禁、签名 Local-only Candidate 与隔离网页 eval 已通过；原生 Bootstrap / Full 人工闭环待执行）

本 PRD 冻结 `0.0.27` 的 Self-evolution Run（自进化运行）范围。它在 [0.0.26 自迭代候选](0023-0.0.26-Sol-自迭代候选闭环产品需求.md) 与 [ADR 0031](../决策档案/0031-自迭代候选来源快照与本机分发边界.md) 之上增加耐久运行回执、重启恢复状态和人工验收，不建立第二套 Session、Goal、Plan、Git 或 Candidate Manifest 权威。难逆转边界由 [ADR 0032](../决策档案/0032-自进化运行回执-bootstrap-与连续门禁边界.md) 固定。

## Problem Statement（问题陈述）

`0.0.26` 已能从明确源码 checkout 生成带完整自动门禁与来源 digest 的本机候选，但“候选是谁构建的、由哪个 Project / Session 发起、实际模型是谁、重启是否进入了目标 App、原 Session 是否恢复、用户是否人工验收”仍是彼此分离的事实。

现有重启标记只有一次性布尔值与 Session ID，App 启动即清除；Host 或会话恢复失败后没有可继续的耐久任务，恢复成功也没有原生回执。D Code 因而不能区分“候选已启动”“原任务已恢复”“用户已验收”与“可发布”，更不能诚实累计 `0.1.0` 所需的连续自进化证据。

已发布的 `v0.0.26` 本身不具备新回执的重启前写入能力，因此 `0.0.26 → 0.0.27` 只能在新 App 恢复后补建 Bootstrap Receipt（引导回执）。它可以证明候选来源、启动与 Session 恢复，但不能倒填不存在的重启前检查，也不计入三次完整自进化循环。第一个可计数的完整循环必须由运行中的 `0.0.27` 在下一次候选重启前发起。

## Solution（解决方案）

1. **耐久 Self-evolution Run。** D Code 本机保存版本化运行记录，引用发起 Project、Pi Session、Host 已确认模型、可选 Active Plan、Candidate Manifest 摘要、起始 / 目标版本与状态时间。记录不复制 Session、Goal、Plan、源码、diff、Prompt、回复或凭据正文。
2. **两种 Assurance（证据保障）。** `legacy_bootstrap` 仅用于 `0.0.26 → 0.0.27` 的恢复后补建；`full_preflight` 必须在候选交换前原子保存 `restart_requested`，并在新 App、manifest、Host 与同一 Session 全部核对后形成完整回执。两者在数据与界面中持续可辨，不以空字段伪装等价。
3. **可恢复状态机。** Full run 依次为 `restart_requested → app_started → session_restored → manual_accepted`；任一恢复失败进入 `recovery_required`，用户可重试恢复或回滚为 `rolled_back`。Bootstrap 从 `app_started` 开始，不能生成重启前时间。
4. **重启前安全门禁。** Full run 只在 Candidate Manifest / 签名 / App-Host 版本有效、当前 Project 目录与源码 checkout 一致、当前 Session 精确属于该 Project、Host 模型为 Sol、没有在途 Run / Prompt transaction / 阻塞交互，且草稿与队列可安全保存时允许重启。不满足时显示具体原因，不替换 App，也不建立可计数回执。
5. **Pending 不提前消费。** Full run 先写入 `restart_requested` 再交换 App。新 App 只能把记录推进到 `app_started`；当前 bundle manifest 与预期版本 / digest 一致、Host ready 且同一 Session 以可写状态恢复后，才进入 `session_restored`。失败记录跨重启保留。
6. **Bootstrap 诚实迁移。** `0.0.27` 启动时若发现 `v0.0.26` 旧重启标记、当前 bundle manifest 与备份版本匹配，则先持久化 `legacy_bootstrap` 的 `app_started` 记录，再清除旧标记；恢复 Session 后补入当前 Project、Host 模型与可选 Active Plan 引用。任一条件不足进入 `recovery_required`，不倒填 `restart_requested`。
7. **重启意图显式分型。** `0.0.27+` 写出的普通候选重启、Full Receipt 重启与 Self-evolution 回滚各有显式 intent 类型；只有无类型、无 Run ID 的 `v0.0.26` marker 可进入 Bootstrap。未终结回执存在时，普通候选交换和普通回滚都必须拒绝，不能覆盖唯一 backup；未知 intent 类型保留并停止自动恢复。
8. **原生运行回执。** 设置页把“本次自进化”的状态与下一动作放在首组，主动作在 `1280 × 800` 首屏可见；来源、门禁、签名与时间线默认下沉到证据详情。恢复后的原 Session 显示轻量状态条，可进入完整回执。
9. **人工验收与连续门禁。** `session_restored` 只表示自动恢复完成；用户必须显式“确认本机可继续使用”或“发现问题 / 回滚”。只有 `full_preflight + manual_accepted` 才计入三次完整自进化循环；Bootstrap 永不计数，验收后仍明确为仅本机、不可分发。
10. **Goal / Plan 只引用。** Active Plan 继续以 Pi / dgoal 结构化状态为事实源；回执最多保存 Goal ID 引用，不保存目标正文，也不把 dgoal 变成所有 Self-build 的运行时依赖。

## User Stories（用户故事）

1. 作为从 `0.0.26` 首次进入 `0.0.27` 的用户，我希望看到诚实的引导回执，从而知道哪些事实可核对、哪些重启前证据并不存在。
2. 作为使用 Sol 继续迭代 D Code 的开发者，我希望重启前明确知道当前 Session 是否安全、候选是否匹配，并在失败后可以继续恢复，而不是失去一次性标记。
3. 作为重启后的验收者，我希望回到同一 Session 后看到版本、digest、模型与可选 Goal 引用，并亲自决定接受或回滚。
4. 作为 `0.1.0` 晋升证据的维护者，我希望只有完整预检且人工验收的真实循环计数，从而不把 Bootstrap、普通启动或模型文案冒充连续自进化。

## Confirmed Constraints（已确认约束）

- Pi Session、Project、Active Plan、Host Model 与 Candidate Manifest 继续由各自现有事实源拥有；Self-evolution Run 只保存引用和有界摘要。
- 本机 store 必须版本化、原子写入、有数量 / 字段上限；损坏或未知版本保留原字节并停止覆盖，不能回退为空成功。
- `legacy_bootstrap` 只适用于已发布 `v0.0.26` 的一次性迁移；不得通过修改旧 tag 或回填时间把它升级为 `full_preflight`。
- 普通 Self-build 继续可用；没有未终结回执时普通本机重启继续可用。只有用户选择“重启并记录自进化”且全部门禁成立时创建 Full run。
- 当前会话有在途模型生成、工具执行、Prompt transaction、未知 Run 或结构化等待时必须拒绝自进化重启；不支持热迁移。
- 人工接受不等于 commit、tag、push、GitHub Release、Developer ID、公证或分发；所有回执持续标记 Local-only。
- App 端自动 GUI eval 当前不可用；隔离网页 eval 只验证状态理解和决策路径，不计入完整循环。

## Eval Scope（评测范围）

- Bootstrap 使用者能否说出“恢复后补建、没有重启前证据、不计入 `1/3`”。
- Full candidate 使用者能否在首屏完成 `restart_requested → app_started → session_restored`，并只在人工验收后理解为完整循环。
- 当前 Run / 工具仍在执行时，使用者能否理解 App 未替换、应回会话收口后重试。
- manifest / Session 恢复失败时，使用者能否拒绝验收并在重试恢复与回滚之间作出有证据的选择。

网页 eval 不证明原生 App、真实 Sol、真实 Pi Session 恢复或完整循环计数。
