# D Code 0.0.29 任务工作台与协调者协作体验产品需求

状态：Implementation Candidate（实现候选；自动门禁待最终回填，原生人工验收、干净候选与发布待完成）

本 PRD 只消费 `0.0.28` 已成立的 Product Store、Task / Session / Run 关系、多 Runtime Supervisor、Coordinator / Child Agent 事实、query / mutation contract 与 Foundation Console 可用闭环，把 D Code 的最终任务工作台 UI/UX 做到位。任何缺失的任务、运行、等待、交付物或环境事实都必须回到 `0.0.28` 修复，不能在本版通过解析聊天文案或增加 UI 私有状态补造。

## Problem Statement（问题陈述）

当前 `0.0.27` 仍以会话作为导航与运行中心，用户一次只能看到和操作一个活动会话。即使 `0.0.28` 已经让一个 Task 拥有协调会话、多个 Child Agent Session 和并行 Run，如果界面仍把它们平铺为独立会话、把 Agent Team 做成静态档案列表，用户仍无法回答：当前任务进展如何、哪些成员在工作、谁在等待我、产生了什么交付物、最终应在哪里继续沟通。

此前原型还把任务进度、Agent Team 和交付物放进从上到下的常驻右栏，挤压中央阅读画布并混淆“任务概览”与“具体对象检查”。已确认方向是：中央默认保持任务对话，协调者就是活在任务对话里的 LLM，不设独立会话入口；Task HUD 在宽度充足时始终以与窗口边缘留出空隙的独立浮窗位于右上留白，Main Workspace 预先保留左右安全区，HUD 更新不改变阅读画布；只有文件、Diff、Artifact、Evidence、Context 来源等具体对象才打开全高 Information Inspector。

## Solution（解决方案）

### 1. 项目 / 任务 → 任务对话 / 子会话导航

- 左侧 Navigation Sidebar 的日常工作对象只有「项目」与「任务」两个分区。Project 展示长期工作集合及其 Task；未选择 Project 的 Task 直接显示在「任务」分区，不显示 User Home、User Scope、“个人任务区”或“未选项目”伪分组。
- 「新建任务」在当前已选择 Project 时创建该 Project 的 Task；没有选择 Project 时创建的 Task 直接进入「任务」分区。两种 Task 进入后使用同一 Task / Session / Run 工作台。
- 导入入口不产生 Task；只有用户点击“导入为任务”、选择加入一个 Project 或不归入 Project 并确认后，才调用 `0.0.28` 原子转换合同创建 Task 与首个 D Code Session。界面不展示 User Scope 这一技术术语。
- 置顶、最近、活动、搜索、归档与设置是功能入口或投影视图，不能成为第三种日常工作对象分区；从其中打开 Task 或 Session 时可以回到原 Project 或「任务」分区的 Task 行。
- Task 主行进入当前任务并默认打开任务对话（Coordination Session）；协调会话不显示为独立的子会话行，任务对话就是它的唯一呈现。展开 Task 后只显示 Child Agent Session 与必要的其他 Task Session，不把子会话重复平铺成顶层 Task。
- Agent Profile 在“设置 > 智能体档案”中呈现可复用配置，不在日常导航中另占工作对象分区；Agent Team 只显示当前 Task 实际启动的 Agent Run，两者不得混称。
- Recent Sessions 可以保留为快速入口，用户文案为「最近工作」：语义上是投影，视觉上仍是一段安静的列表，位于创建动作之后、项目树之前，不降级为按钮，也不成为第三对象分区；每个条目必须能返回所属 Task，Recent 不成为第二任务导航。
- 切换当前查看的 Task / Session 只改变视图选择，不关闭、暂停或迁移 `0.0.28` 的后台 Runtime。

### 2. 任务对话（协调者在此）

- 中央默认显示任务对话（Coordination Session），并明确标注协调者在此对话中工作。协调者就是活在任务对话里的 LLM，不是需要单独入口的子窗口；用户的普通任务沟通、目标校准、成员问题去重和最终综合都回到这里。
- Coordinator 的派发、成员请求、报告到达、冲突和综合结果以 D Code 原生对象呈现，不伪装成用户消息，也不展示隐藏 Thinking。
- 用户可以进入任一 Child Agent Session 查看该成员的有界上下文、当前活动、工具、报告和证据；返回任务对话不会停止该成员或其他 Runtime。
- Coordinator 可以提出 Task 验收请求。验收卡由一句话请求、一个反馈输入框和单一确认动作组成：输入框为空时确认即接受，产生结构化验收事实；输入框有内容时确认即把反馈绑定本验收请求提交，协调者按反馈返工，验收保持待定。不设独立的「要求返工」动作；接受不由模型文案推导，暂停或结束 Task 仍由用户决定。`0.0.29` 先支持有界文本反馈；图片附件必须等 D Code 受管附件 / Artifact 合同成立后再开放，不能静默丢失。

### 3. Task HUD（任务浮层）

Task 存在时，Task HUD 始终承担任务级概览：

- **宽屏 `≥1320 pt`**：HUD 持续以独立圆角浮窗显示在 Main Workspace 右上 gutter（留白区），与顶边、右边、底边保持外侧间距，不提供整体关闭按钮；它的首选最大高度为 `620 pt`，超出的分区在浮窗内滚动，不能拉成全高第三栏。Main Workspace 在布局开始前为阅读与 Composer 预留左右安全区，中央阅读画布保持固定首选宽度和位置，HUD 不挤压、不移动、不覆盖正文。
- **中宽 `880–1319 pt`**：HUD 才允许覆盖阅读区域，并提供收起 / 再打开入口；收起只改变呈现，不停止 Run 或删除任务事实。
- **紧凑 `640–879 pt`**：在当前最小支持窗口内初始只保留“任务概览”入口，用户打开后以内容高度浮层覆盖，不进入普通文档流。
- HUD 的 Progress、Agent Team、Waiting 和 Deliverables 分区可以独立折叠；宽屏不能永久隐藏整个 HUD。
- HUD 只消费 `0.0.28` 的 Task、Work List、Agent Run、Agent Request、Artifact 与 Evidence 结构化投影；等待事项由开放状态的结构化 Request / 验收请求按当前 Task 过滤直接得出，不新建独立的 attention 存储或 UI 私有状态，也不从模型文案、会话更新时间或动画猜状态。

### 4. HUD 内容与操作

- Progress 显示 Task Goal、当前阶段、Work List 完成 / 进行 / 阻塞、最近证据以及是否等待用户验收。
- Agent Team 显示每个实际 Agent Run 的角色、名称、模型、状态、当前活动、等待请求、耗时 / 用量和报告入口；选择成员打开对应 Child Agent Session。
- Waiting 把需要用户回答、批准、处理失败或验收结果的请求放在任务语境中；回答一个成员不改变其他成员运行。等待事项与任务对话中的对象卡是同一结构化对象（同一 ID / revision）的两个等价入口：任一处操作后另一处同步消解，不复制状态，也不残留可重复操作的按钮。
- Deliverables 按 Artifact 类型与稳定身份组织交付物；选择条目在中央 Workspace Tab 打开内容，选择“查看详情”才进入 Information Inspector。
- 用户可以从 HUD 停止单个 Agent Run、回答结构化 Request、查看 Report / Evidence 或进入 Task 验收（验收反馈经任务对话中的验收卡提交）；危险操作必须明确目标成员和影响范围。

### 5. Information Inspector（信息检查器）

- Information Inspector 只用于需要持续检查的具体对象：文件、Git Diff、Artifact、Evidence、Report、Context 来源、Agent Environment、Prompt / Tool Receipt，以及当前 Session / Task 本身。Session / Task 的检查视图承载会话概览（消息数、Session ID）、工作目录与运行证据入口，取代旧右栏的常驻会话页签；这些元信息不进入 Task HUD。
- 它以全高右侧栏出现，显示对象路径、来源、revision、引用关系、变更和适用操作；不承载 Task Progress、Agent Team 或交付物总览。
- 打开 Inspector 时 Task HUD 暂时让出；关闭后 HUD 自动恢复。两者不在同一位置叠加，也不互相复制状态。
- 选择对象、打开 Inspector 或 Workspace Tab 不会自动加入模型 Context、修改文件、改变 Git 状态或启动 Agent。

### 6. Composer 与运行控制

- Coordination Session Composer 是默认任务输入；Child Session Composer 明确表示消息将进入哪个成员，避免把补充上下文误发给协调者或其他 Agent。
- `Abort（停止）`、当前 Runtime 的模型选择与推理强度全部绑定确切 Session / Run；当前查看对象变化不会让控制目标漂移。模型 / 推理只影响当前 Runtime，不伪装成未来 Runtime 的默认模型设置。
- 当多个 Run 同时活动时，界面显示每个停止操作的目标，不提供含糊的全局“停止所有”默认动作。
- `Queue（后续消息队列）` 与 `Steer（即时介入）` 不进入本版 UI：现有实现分别是旧 App 私有 JSON 与 Pi Runtime 调用，尚未拥有 D Code Raw Input / Effective Input / Product Store 合同。`0.0.29` 不显示会造成数据丢失或身份漂移的半成品入口；后续版本须先补原生基础设施，再进入任务对话。

### 7. 恢复与用户关注

- App 重启后恢复 Project / Task、当前选中 Session、阅读位置、Composer Draft、HUD 分区状态、Inspector 对象、未处理 Request、Report、Artifact 与 Evidence。
- 重启前正在运行的 Runtime 按 `0.0.28` 恢复为 interrupted / unknown，不显示仍在生成或虚假进度动画。
- Task Run State 与 User Attention 分开：运行完成后可以继续等待用户查看或验收；打开 HUD 本身不清除关注态。

### 8. Native macOS 体验与无障碍

- 界面使用 SwiftUI / AppKit 原生菜单、焦点、键盘、VoiceOver、语义色和系统字体，不复刻 MiniMax Code 的品牌皮肤或 Electron 组件。
- Task、会话、智能体、进度、交付物和等待事项使用中文主标签；模型名、命令、路径和代码标识符保留原文。
- Hover、选中、焦点、状态变化和面板开合不推动标题、中央阅读画布或相邻控件；Reduce Motion / Transparency 与 Increase Contrast 下关键关系仍清楚。
- HUD、Navigation Sidebar、Information Inspector 与中央阅读画布具有独立可访问区域和键盘入口；没有只靠颜色、Hover 或鼠标才能完成的操作。

### 9. 从 Foundation Console 迁移到正式工作台

- `0.0.29` 复用 `0.0.28` 已验收的 query / mutation contract、对象 ID、revision、幂等请求和事件；只替换信息架构、组件和交互层级，不改变运行语义。
- Foundation Console 中创建 Task、开始 / 停止 Run、回答 Request、查看报告和验收的能力必须在正式工作台具有等价入口；切换 UI 不迁移或复制 Product Store 对象。
- 正式工作台覆盖相应路径并通过回归后，旧 Foundation Console 的普通用户入口退出；必要诊断信息可以保留在 Host Diagnostics，但不能长期存在两套并列任务操作界面。

## User Stories（用户故事）

1. 作为正在推进复杂 Task 的用户，我希望点开任务就直接和活在任务对话里的协调者继续工作，并能展开查看各个子 Agent，而不会把协调者当成又一条会话或把多个会话误认为多个任务。
2. 作为同时运行两个成员的用户，我希望宽屏 Task HUD 持续显示真实进度、等待和交付物，同时中央内容保持稳定可读。
3. 作为需要核对具体文件或证据的验收者，我希望打开全高 Inspector 深入检查，并在关闭后回到原任务概览。
4. 作为窄窗口用户，我希望 Task HUD 只在必要时覆盖并可收起，而不是永久挤压或隐藏对话。
5. 作为重启后的用户，我希望回到同一 Task、当前会话和未处理请求，同时清楚知道哪些 Runtime 已经中断。

## Confirmed Constraints（已确认约束）

- `0.0.29` 只消费 `0.0.28` 的结构化事实，不新建 UI 私有 Task / Run / Artifact 状态，不解析模型文案推导完成度。
- `0.0.29` 复用 Foundation Console 的生产级操作合同；缺失操作必须回到 `0.0.28` 补齐，不能新增只服务新界面的旁路 mutation。
- Task 是产品根；Coordination Session、Child Agent Session、Agent Run、模型和 HUD 都不拥有 Task。
- Task HUD 是持续任务概览，不是第三个结构栏位；Information Inspector 是具体对象详情，不是任务总览。
- Agent Profile 与实际 Agent Run 分开；保存或选择 Profile 不启动成员，运行时显示实际模型、工具和职责快照。
- 切换视图不改变 Runtime；停止、回答、返工与验收必须绑定明确对象并保留可恢复结果。
- 用户原话、Effective Input、Prompt、工具、报告和 UI 摘要保持来源区分；界面摘要不得覆盖原事实。
- 实现、自动 UI 测试、真实并行运行、人工宽窄屏 / VoiceOver 验收、候选构建、commit、tag 与发布分别成立。

## Acceptance Criteria（验收标准）

### 导航与协调会话

- [ ] 左侧日常工作对象只分为「项目」与「任务」：每个 Project 行下显示其 Task；未选择 Project 的 Task 直接显示在「任务」分区。不存在可点击的 User Home、User Scope、“个人任务区”或“未选项目”中间容器。
- [ ] 「新建任务」在已选择 Project 时落入该 Project，未选择 Project 时直接显示在「任务」分区；两种 Task 均使用相同的任务对话、计划、工作清单、Agent Run、产物、证据与验收路径。
- [ ] Task 主行即任务对话入口，协调会话没有独立导航行，展开 Task 后只显示 Child Agent Session，子会话不重复成为顶层 Task。
- [ ] 非 Project Task 的默认 `cwd` 为用户 Home Directory，但界面不暴露该目录或 `~/.dcode/`，也不把它伪装成 Project。
- [ ] Pi Session 预览与“导入为任务”是显式两步；取消不创建对象，确认后产生一个新 Task 与首个 D Code Session。导入界面只提供加入 Project 或不归入 Project 的选择，说明不修改源 JSONL 的边界，不显示 User Scope 这一技术术语。
- [ ] 打开 Task 默认进入任务对话，界面明确表达协调者在此对话中；进入 Child Session 与返回任务对话不会停止任何 Runtime。
- [ ] “设置 > 智能体档案”中的 Agent Profile 与当前 Task HUD 的 Agent Team 明确分开，Profile 不显示成正在工作的成员，也不在日常导航中成为第三种分区。

### Task HUD

- [ ] `≥1320 pt` 时 HUD 始终以与窗口边缘分离的独立浮窗显示且没有整体关闭入口；HUD 的顶、右、底外缘均可见，首选最大高度为 `620 pt`，超出时只滚动其内部，不能形成全高第三栏。中央阅读画布宽度、横向位置、滚动位置在 HUD 更新前后保持不变，二者没有像素重叠。
- [ ] `880–1319 pt` 时 HUD 才进入覆盖态并可以收起 / 恢复；`640–879 pt` 初始只显示“任务概览”入口，展开后仍是浮层而非普通流式内容。
- [ ] HUD 的进度、成员、等待事项和交付物与 `0.0.28` 同一 Task revision 一致；任何未知字段显示未知，不用零值或文案猜测。
- [ ] 选择成员、回答 Request、停止单个 Run 或查看 Artifact 只影响明确目标，其他 Run 继续且状态不漂移。
- [ ] 同一 Request / 验收请求在任务对话对象卡与 HUD 等待分区双入口等价；任一入口操作后另一入口在同一 revision 消解，不出现可重复操作的残留按钮。
- [ ] 验收卡呈现一句话请求、一个反馈输入框与单一确认动作：空内容确认产生结构化接受事实；非空有界文本确认把反馈绑定验收请求提交并保持待定；不存在独立「要求返工」入口，确认动作的当前语义在按钮上可辨。图片附件未出现为可点击但无处落库的假入口。

### Inspector 与对象查看

- [ ] 只有文件、Diff、Artifact、Evidence、Report、Context 来源、Agent Environment、Receipt 或当前 Session / Task 对象打开全高 Inspector；会话概览与工作目录经 Session / Task 检查视图呈现，Task Progress / Team / Deliverables 不进入该栏。
- [ ] 打开 Inspector 时 HUD 暂时让出，关闭后自动恢复原分区状态；中央 Workspace Tab 与会话草稿不被重建。
- [ ] 打开对象和详情不会自动加入 Context、写文件、改变 Git 或启动 Agent。

### 并行状态与恢复

- [ ] Coordinator + 两个 Child Agent 并行运行时，左侧会话树、中央当前会话和 HUD 对成员状态、等待、报告与交付物显示一致。
- [ ] 一个成员 waiting、一个 running、一个 completed 的混合状态可以同时呈现；回答或停止其中一个不会阻塞其他成员。
- [ ] 重启后恢复 Task、选择、草稿、HUD、Inspector 与未处理结果；在途 Runtime 显示 interrupted / unknown，不伪装继续运行。

### 原生体验与验证

- [ ] Swift 自动测试覆盖 Task / Session 导航、HUD 三类宽度、Inspector 互斥、控制目标、并行事件错序、恢复与无障碍标签；现有 Host / Swift 全量回归通过。
- [ ] 使用真实 `0.0.28` 数据完成宽屏、中宽、紧凑三类窗口人工路径；核对深浅色、键盘、VoiceOver、Increase Contrast、Reduce Motion 与长中文标题。
- [ ] 人工验收至少真实启动 Coordinator + 两个 Child Agent，进入每个子会话、回答一个 Request、停止一个成员、查看一个 Artifact / Evidence，并由用户在任务对话完成验收决定。
- [ ] Foundation Console 的所有用户操作在正式工作台都有等价入口并作用于同一对象 ID / revision；旧普通入口退出后没有双 UI、双写或行为差异。

## Eval Scope（评测范围）

- 用户能否在不理解 Session / Run 技术细节的情况下说出当前 Task 进展、谁在做什么、哪里需要自己处理。
- HUD 宽屏常驻是否以独立浮窗使用预先定义的左右安全区，而非变成第三栏、暗中缩窄或随 HUD 状态移动中央画布；窄屏覆盖是否可恢复。
- 用户从 Child Session 返回主任务时，是否理解成员仍在后台运行且 Coordinator 仍是默认沟通入口。
- 文件详情、任务概览和 Agent 环境是否使用正确容器，不再混成一个万能右栏。
- 重启后的 interrupted / unknown 是否足够诚实，不把旧动画或模型文案当作运行事实。

## Out of Scope（非目标）

- 修改 `0.0.28` Product Store、Runtime Supervisor、Prompt / Tools、Pi 导入或并发所有权合同；发现缺口必须回到基础设施版本修复。
- D Code 原生 `Queue（后续消息队列）`、`Steer（即时介入）` 与验收反馈图片附件：它们需要先建立新的 Product Store / Raw Input / Effective Input / 受管 Artifact 合同，不复用旧 App JSON 或 Pi 直连接口。
